1. 5분 만에 내 프로젝트 시작

이 저장소는 복제해서 쓰라고 만들어졌다. 카운터 하나가 UI → API → DB → 마이그레이션 → 테스트 → CI를 관통하는 레퍼런스 슬라이스이고, 그걸 걷어낸 자리에 여러분의 도메인을 넣는 것이 사용법이다.

새 프로젝트를 만든다

make create NAME=my-app          # 옆 디렉터리에 새 저장소 (BARE=1이면 카운터 없이)
cd ../my-app
make bootstrap                    # 의존 설치 → db·broker 기동 → 마이그레이션
make dev                          # 스캐폴더가 고른 포트로 (기본 http://localhost:3000)

스캐폴더가 하는 일: 이름 치환(package.json·README·앱 헤더) · 비어 있는 포트를 골라 .env에 기록 (DB_PORT↔DATABASE_URL 짝까지 함께) · git 초기화 · 훅 설치 · 어느 세대의 템플릿에서 나왔는지 기록.

템플릿 자체를 보려면

git clone <repo> && cd tarae-web-stack
make bootstrap && make dev
도메인(URL)은 아직 없어도 된다. 기본이 http://localhost:3000이고, 나중에 도메인을 사면 .env의 APP_URL만 바꾸면 된다 — 코드와 빌드 산출물에는 도메인이 들어 있지 않다.

3. 요청 하나가 지나가는 길

화면에서 증가를 누르면 어떤 파일이 순서대로 실행되는가. 이 절만 따라가면 구조가 잡힌다.

[브라우저] 증가 버튼 클릭 │ frontend/app/components/CounterClient.tsx — act("increment") ↓ POST /api/counter.v1.CounterService/ApplyCounter (Connect unary · JSON) frontend/server.mjs 요청 로그 · x-request-id 발급 · x-forwarded-for 기록 · Next에 위임 ↓ app/api/[...path]/route.ts 프록시 — 경로를 고치지 않고 api로 넘긴다 ↓ (서버 렌더는 이 단계를 건너뛰고 api를 직접 부른다) backend 인터셉터 체인 ① 요청 로그 → ② rate limit(IP별·읽기/쓰기 분리) ↓ → ③ 검증(protovalidate) → ④ 오류 변환 │ 검증 규칙은 .proto에 선언돼 있다 — 핸들러에 검증 코드가 없다 ↓ internal/counter/handler.go proto → 도메인 변환 후 서비스 호출 ↓ internal/counter/service.go 규칙: idempotent 재전송이면 즉시 반환 · 0 floor(하한) · 커밋 뒤에만 propagation ↓ internal/counter/repo.go sqlc 생성물 호출 → queries/counter.sql 의 한 문장 ↓ UPDATE … SET value = GREATEST(value+1, 0) … RETURNING internal/db → PostgreSQL (pgxpool — 프로세스당 하나) ↓ internal/realtime/bus.go Publish(ctx, "default") — 값이 아니라 이름만 브로커로 ↓ ├─→ 같은 backend의 스트림·WS 구독자 handler.go의 WatchCounter · ws.go └─→ 다른 backend 인스턴스의 구독자 (Redis pub/sub을 거쳐 도달) ↓ [각 구독자] 이름을 받고 최신 값을 다시 읽어 델타 전송 ↓ WS는 frontend/server.mjs의 터널을 지나 브라우저로 → 화면 갱신
왜 propagation에 값을 싣지 않는가 — 메시지 순서가 뒤바뀌거나 유실돼도 낡은 값이 화면에 남지 않는다. 그래서 브로커에 영속성이 필요 없고, 페이로드에 민감 데이터가 흐르지 않는다. 대가는 알림 1건당 읽기 1회다.

4. 입구 — frontend/server.mjs

브라우저가 보는 주소는 web 하나뿐이다. web은 세 가지를 한다 — 화면을 그리고, /api/*를 api로 넘기고, /ws 업그레이드를 api로 터널링한다. Next를 커스텀 서버로 띄우는 이유는 하나다: Route Handler는 요청→응답 모델이라 HTTP 업그레이드(101)를 만들 수 없다.

ADR-002 시절과 달리 여기는 실시간의 종단이 아니다. 종단은 api의 게이트웨이이고, 이 파일은 소켓 두 개를 이어 붙이는 일만 한다. 그래서 메시지 종류가 늘어도 이 파일은 바뀌지 않는다.

  //   화면의 JSON.parse가 "[object Blob]"에서 터진다.

  client.on("message", (data, isBinary) => {

요청은 두 번 손을 탄다. web의 프록시는 아무것도 판단하지 않고 넘기기만 하고, api의 핸들러가 계약 타입을 도메인 타입으로 옮겨 서비스를 부른다.

func (h *Handler) ApplyCounter(ctx context.Context, req *connect.Request[counterv1.ApplyCounterRequest]) (*connect.Response[counterv1.ApplyCounterResponse], error) {
	c, replayed, err := h.svc.Apply(ctx, req.Msg.GetName(), fromProtoOp(req.Msg.GetOp()), req.Msg.GetIdempotencyKey())
	if err != nil {
		return nil, err   // 오류는 **그냥 돌려준다** — middleware가 Connect 코드로 옮긴다
	}
	res := connect.NewResponse(&counterv1.ApplyCounterResponse{Counter: toProto(c), Replayed: replayed})
	// 헤더로도 알려 준다 — 프록시 로그나 curl로 확인할 때 본문을 파싱하지 않아도 되게.
	res.Header().Set("X-Idempotent-Replay", boolStr(replayed))
	return res, nil
}

읽어야 할 지점:

  • 검증 코드가 한 줄도 없다 — 규칙을 .proto에 선언했고(protovalidate) 인터셉터가 자동으로 적용한다. 잘못된 이름은 핸들러에 닿기 전에 400 invalid_argument로 끝난다.
  • rate limit도 여기 없다 — main.go가 인터셉터로 한 번 건다. 핸들러마다 붙이면 새 RPC가 빠뜨렸을 때 조용히 무방비가 된다.
  • proto 타입은 이 파일 밖으로 나가지 않는다 — toProto/fromProtoOp가 경계다. 계약이 바뀌어도 규칙은 그대로다.

9. 실시간 — realtime/ · 서버 스트리밍 · WebSocket

두 실시간 채널이 하나의 convention을 공유한다: snapshot 먼저, 그다음 delta. 붙자마자 전체 상태를 한 번 받고 이후엔 변화만 받는다. 끊겼다 다시 붙으면 또 snapshot을 받으므로 끊긴 사이의 변화가 저절로 메워진다 — 이벤트를 재생할 필요가 없다.

// 조작 — 규칙은 service가 판정한다. 여기서 값을 만들지 않는다.
op, ok := wsOp(cmd.Type)
if _, _, err := h.svc.Apply(ctx, cmd.Name, op, ""); err != nil {
	_ = send(wsMessage{Type: "error", Detail: userMessage(err)})
	continue
}
// 결과는 propagation을 타고 위 goroutine이 델타로 보낸다 —
// 그래서 이 소켓과 다른 탭·다른 인스턴스가 **같은 경로로** 같은 값을 받는다.

WebSocket은 규칙을 갖지 않는다. 메시지를 파싱해 스트리밍·unary와 같은 service를 부르므로 idempotency·0 floor(하한)·propagation이 채널과 무관하게 똑같이 적용된다 — "WS만 규칙이 다른" 사고가 구조적으로 생기지 않는다.

프레임은 텍스트(JSON)다. 바이너리로 보내면 브라우저에서 event.data가 Blob이 되어 JSON.parse가 터진다(실측으로 겪은 함정 — node 스모크는 통과하고 브라우저에서만 깨졌다). 알 수 없거나 깨진 메시지에도 연결을 끊지 않는다. 대신 30초 ping에 두 번 연속 응답이 없으면 끊는다.

          method: "POST",
          headers: { "content-type": "application/json", "idempotency-key": crypto.randomUUID() },
          body: JSON.stringify({ op }),
        });
        if (!r.ok) throw new Error((await r.json()).detail ?? `HTTP ${r.status}`);
        setSnap(await r.json());
        await refreshList();
      }
    } catch (e) {
      const detail = String(e instanceof Error ? e.message : e);
      setErr(detail);

      toast(detail, "error");

3단계 — 규칙을 쓴다

backend/internal/order/service.go의 Advance를 도메인에 맞게 고친다. 예를 들어 "제출된 주문은 취소할 수 없다":

var allowed = map[string][]string{
	"draft":     {"submitted", "cancelled"},
	"submitted": {"paid"},              // 취소가 빠졌다 — 이 한 줄이 규칙이다
	"paid":      {"refunded"},
}

func (s *Service) Advance(ctx context.Context, name, next string) (Order, error) {
	cur, err := s.GetOrCreate(ctx, name)
	if err != nil { return Order{}, err }
	if !slices.Contains(allowed[cur.Status], next) {
		return Order{}, errs.New(errs.Conflict, "%s → %s 전이는 허용되지 않습니다", cur.Status, next)
	}
	…
}

이 판정이 service.go에만 있다는 점이 중요하다. RPC로 부르든 WebSocket으로 부르든 배치에서 부르든 같은 판정이 나온다.

15. 지켜야 할 7가지

나머지는 취향이지만 이 일곱은 지켜야 한다. 어기면 이 템플릿의 성질이 사라진다.

1
service는 HTTP를 모른다

Request/Response/헤더/쿠키/Next를 import 하지 않는다. 그래야 세 채널이 같은 규칙을 쓰고, 테스트가 인프라 없이 돈다.

2
서버 데이터를 전역 스토어에 넣지 않는다

첫 값은 RSC props, 이후는 구독. 전역에 올리는 순간 "언제 무효화하나"가 따라온다.

3
모듈 최상단에서 설정을 읽지 않는다

빌드가 런타임 설정을 요구하게 되어 같은 이미지를 여러 환경에 못 올린다. db·bus·idempotency는 첫 사용 때 만들어진다.

4
갱신은 한 문장으로

읽고-쓰기 대신 UPDATE … RETURNING. 동시 요청에서 갱신이 유실되지 않는다.

5
propagation에는 이름만, 커밋 뒤에

값을 실으면 순서가 뒤바뀔 때 낡은 값이 남는다. 커밋 전에 보내면 구독자가 옛 값을 읽는다.

6
앱은 마이그레이션을 스스로 돌리지 않는다

인스턴스가 동시에 뜰 때 같은 DDL이 겹친다. one-shot·idempotency으로 분리한다.

7
설정이 없으면 뜨지 않는다

조용히 떠서 첫 요청에 500을 내는 것이 가장 나쁘다. 부팅에서 죽고 누락 항목을 알린다.
