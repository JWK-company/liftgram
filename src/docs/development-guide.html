1. 5분 만에 띄우기

처음 이 저장소를 받았다면 이 네 줄이면 된다.

# 1) 설정 파일을 만들고  2) 의존 설치 + 인프라 + 마이그레이션
make bootstrap
# 3) 개발 서버
make dev        # http://localhost:3000

전부 컨테이너로 돌리고 싶다면 한 줄이다. 이미지 빌드 → db·broker·마이그레이션·앱 기동 → smoke test까지 자동으로 이어진다.

make up-all     # 전부 올린다 (빌드 → 기동 → 헬스 대기 → smoke test 11종)
make down-all   # 전부 내린다 (스택 · 개발 인프라 · 추가 인스턴스 · 남은 프로세스)
make status     # 지금 뭐가 떠 있나 (컨테이너 · 포트 · 헬스)
순서는 항상 인프라 → 마이그레이션 → 앱이다. 앱은 마이그레이션을 스스로 돌리지 않는다. 컨테이너에서도 migrate one-shot이 정상 종료해야 backend가 뜬다.

2. 명령 지도 — make

make 만 치면 아래 목록이 그대로 나온다. 파트는 다섯이고, 각 파트는 서로를 기다리지 않고 따로 올리고 내릴 수 있다.

③ 데이터generate → migrate
generate-custom NAME=…

자주 쓰는 흐름

# 아침에 작업 시작
make infra-up && make dev

# 스키마를 바꿨다

# 커밋 전

# 프로덕션과 같은 조건으로 확인
make up-all && make scale-2      # 두 탭으로 :3000 과 :3002 를 열어 비교
make down-all

3. 화면 둘러보기

아래는 프로덕션 이미지를 컨테이너로 띄운 상태에서 찍은 것이다. 오른쪽 끝 타일 이 페이지를 준 인스턴스가 응답한 컨테이너의 호스트명이다.

두 인스턴스 사이의 실시간 propagation

왼쪽은 두 번째 인스턴스가 준 화면이고, 증가 버튼은 다른 인스턴스에서 눌렀다 — 값이 함께 움직이면 브로커를 실제로 거친 것이다.

4. 소스 트리와 경계

디렉터리마다 README가 있다 — 클릭해서 바로 내려갈 수 있다: proto · backend · database · frontend · contracts · scripts. Claude Code로 작업한다면 CLAUDE.md가 색인이다.

my-app/
├─ CLAUDE.md                  구조·작업 흐름 색인(Claude Code가 자동으로 읽는다)
│
├─ proto/<도메인>/v1/*.proto   ① 계약 — single source of truth(검증 규칙도 여기 선언)
│                               make proto → Go·TS 생성물이 함께 갱신된다
├─ frontend/                 ② 화면과 입구 — 브라우저가 보는 유일한 주소(:3000)
│  ├─ server.mjs              프로세스 입구. HTTP는 Next에, /ws는 backend로 터널링
│  ├─ app/
│  │  ├─ layout.tsx              앱 셸(헤더·푸터·토스트 루트)
│  │  ├─ page.tsx             RSC — 서버에서 backend를 불러 초기값을 확정해 내린다
│  │  ├─ components/            화면 조각 (States = 로딩·빈·오류 3종 표준)
│  │  └─ api/[...path]/route.ts  ③ 프록시 — /api/* 를 backend로 그대로 넘긴다
│  ├─ lib/api.ts · lib/env.ts   backend 주소를 아는 유일한 곳 · 화면 설정
│  └─ e2e/                      브라우저 테스트(Playwright)
│
├─ backend/                  ④ 도메인 — 밖에서 보이지 않는다(:3001 · Go)
│  ├─ cmd/server/main.go        composition root — 인터셉터 체인(로그→제한→검증→오류변환)
│  ├─ cmd/migrate/main.go       one-shot 마이그레이션 러너
│  └─ internal/
│     ├─ config/                설정을 읽는 유일한 곳. 없으면 부팅 실패
│     ├─ <도메인>/            ⑤ 도메인 — service(규칙만) · repo(변환) ·
│     │                            handler(Connect) · ws(양방향) · service_test(2ms)
│     ├─ db/                    연결 풀 · 마이그레이션 실행 · sqlcgen(생성물)
│     ├─ realtime/bus.go        ⑥ propagation 추상화 — publish/subscribe
│     └─ middleware/            request-id · rate limit · 오류 매핑

│  ├─ migrations/*.sql        schema의 source of truth · sqlc도 이걸 읽는다

├─ contracts/                   계약의 TypeScript 면(gen/ 은 생성물)

의존은 한 방향으로만 흐른다. app/ → services → service → repository → db. 반대 방향 화살표가 없어서 안쪽을 바꿔도 바깥이 깨지지 않고, 안쪽은 바깥 없이 테스트된다.

층아는 것모르는 것그래서 얻는 것
app/HTTP · React · Next규칙 · SQL프레임워크가 바뀌어도 여기만 바뀐다
service규칙HTTP · SQL · propagation 구현REST·WS·배치가 같은 함수를 부른다
repositorySQL규칙쿼리 튜닝이 규칙을 건드리지 않는다
buspropagation도메인인메모리↔Redis 교체에 도메인 0줄
각 파일 머리 주석에 그 파일의 책임·지킬 것·확장하는 법이 적혀 있다. 손대기 전에 그 열 줄만 읽으면 패턴에서 벗어나지 않는다.

5. 세 채널 convention

채널방향위치쓸 때
unary요청 → 응답backend internal/counter/handler.go쓰기 · 조회 · idempotency가 필요한 것
서버 스트리밍서버 → 클라backend handler.go의 WatchCounter알림 · 진행률 · 읽기 전용 실시간
WebSocket양방향server.mjs 의 /ws커서 · 협업 · 저지연 양방향

셋 다 스냅샷 먼저, 그다음 델타다. 클라이언트는 붙자마자 전체 상태를 한 번 받고, 이후에는 변화만 받는다. 끊겼다 다시 붙으면 또 스냅샷을 받으므로 끊긴 사이의 변화가 저절로 메워진다 — 이벤트를 재생할 필요가 없다.

propagation에 값이 아니라 이름만 싣는다

// service.go — 값을 바꾼 뒤
s.bus.Publish(ctx, name)      // "이 카운터가 바뀌었다"만 보낸다

// 받는 쪽(스트리밍·WS)은 각자 최신값을 다시 읽는다
c, _ := s.Get(ctx, name)
send(KIND_DELTA, c)
  • 메시지 순서가 뒤바뀌어도 낡은 값이 화면에 남지 않는다
  • 메시지를 잃어도 다음 알림이나 재연결 스냅샷이 덮는다 → 브로커에 영속성이 필요 없다
  • 페이로드에 민감 데이터가 흐르지 않는다

입력 convention — 도메인에 닿기 전에 거른다

검증은 src/lib/validation.ts 한 곳에 모여 있다. 라우트마다 다르게 파싱하면 어떤 엔드포인트는 500자 이름을 받고 어떤 엔드포인트는 안 받는 식으로 갈라진다.

대상규칙어길 때
리소스 이름(:name)1~64자 · 영문/숫자/-/_/. (앞뒤 공백 제거)400 problem+json
limit1~50 정수(기본 20)400 — 조용히 고치지 않는다
cursor이름과 같은 규칙400
요청 본문없거나 빈 문자열이면 기본값 적용, 깨진 JSON은 거절400

이름을 좁게 잡은 이유: 이름은 URL과 propagation 메시지에 그대로 실린다. 공백·슬래시·제어문자가 섞이면 로그·라우팅·구독 키에서 사고가 난다. 한글 등으로 넓혀야 하면 nameSchema 한 곳만 고치면 된다.

모든 응답에 x-request-id가 실리고, 서버 로그의 같은 값으로 그 요청을 찾을 수 있다. 로그는 한 줄 = JSON 한 개다:

{"ts":"2026-07-27T…","level":"warn","msg":"request","requestId":"1eedd303-…",
 "method":"GET","path":"/api/counters","status":400,"ms":2}

6. 확장 레시피

새 API 모듈(도메인) 추가

가장 자주 하게 될 작업이다. 이 여섯 단계를 지키면 REST·SSE·WS 세 채널이 저절로 따라온다.

// 1) proto/order/v1/order.proto — contract가 source of truth. 여기서 시작한다
message Order { string id = 1; string name = 2; string status = 3; }
rpc AdvanceOrder(AdvanceOrderRequest) returns (AdvanceOrderResponse) {}

// 2) database/migrations/000N_create_orders.sql — 테이블(= sqlc의 schema의 source of truth)
CREATE TABLE IF NOT EXISTS orders ( id uuid PRIMARY KEY …, status text NOT NULL DEFAULT 'draft' );

// 3) database/queries/order.sql — SQL만. 규칙 금지
-- name: SetOrderStatus :one
UPDATE orders SET status = @status, updated_at = now() WHERE name = @name RETURNING …;

// 4) backend/internal/order/service.go — 규칙만. connect·proto·pgx 금지
func (s *Service) Advance(ctx context.Context, name, next string) (Order, error) {
  if !slices.Contains(allowed[cur.Status], next) {
    return Order{}, errs.New(errs.Conflict, "%s → %s 전이는 허용되지 않습니다", cur.Status, next)
  }
  row, err := s.repo.SetStatus(ctx, name, next)
  s.bus.Publish(ctx, name)          // propagation은 커밋 뒤에 — 이름만 나간다
  return row, err
}

// 5) backend/internal/order/service_test.go — 가짜 저장소로 규칙만 검증(DB·서버 없이)

// 6) backend/cmd/server/main.go — composition root에 네 줄(make gen 이 자동으로 넣는다)
orderRepo := order.NewRepo(pool)
orderSvc := order.NewService(orderRepo, bus)
orderPath, orderHTTP := orderv1connect.NewOrderServiceHandler(order.NewHandler(orderSvc), opts)
mount(mux, orderPath, orderHTTP)

// → make proto && make sqlc && make migrate && make verify

새 동작(op) 추가

  1. repository.ts에 SQL 함수 — 갱신은 한 문장(UPDATE … RETURNING)으로
  2. service.go의 Op에 이름 추가 + 분기 한 줄
  3. service_test.go에 경계값·idempotency 테스트
  4. .proto의 enum에 값 추가 → make proto (화면·서버가 함께 따라온다) · ws.go의 메시지 목록에도 추가

새 채널 / 새 버튼 (클라이언트 상태)

상태는 다섯으로 나뉘어 있다. 뭉치면 "값은 왔는데 연결은 끊긴" 같은 상태를 표현할 수 없다.

상태의미
snap서버가 준 현재 상태 — 화면의 단일 진실
rows목록(별도 조회 결과)
channel어느 방식으로 받는가 — 사용자의 선택
conn연결이 살아있는가 — 전송 계층의 사실
busy / err조작의 진행·실패 — 화면의 사실
// 채널 추가: 유니온 + 버튼 배열 + useEffect 분기(정리 함수 필수)
type Channel = "rest" | "sse" | "ws" | "poll";

useEffect(() => {
  if (channel === "poll") {
    setConn("connected");
    const t = setInterval(refresh, 3000);
    return () => { clearInterval(t); setConn("closed"); };   // ← 이 줄을 빠뜨리면 누수
  }
  // …
}, [channel]);

7. 환경변수

값을 읽는 곳은 각 단위에 하나씩이다 — backend/internal/config/config.go·frontend/lib/env.ts. 코드 어디서도 process.env를 직접 읽지 않는다. 우선순위는 실제 환경변수 > .env 파일 > 스키마 기본값이며, 컨테이너에는 .env가 없고 환경변수만 들어온다.

설정이 어긋나지 않게 하는 장치

make env-init    # .env가 없으면 .env.example에서 만든다(있으면 안 건드린다)
make env-check   # 두 스키마·.env·.env.example 대조 + 짝 검사(포트↔URL) + 지금 설정으로 실제 검증
make env-diff    # 내 .env와 예시의 키 차이만
make env-print   # 지금 적용되는 값(비밀번호는 가림)
$ make env-check

  설정 키 — 설정 코드 기준 (backend/internal/config/config.go · frontend/lib/env.ts)

    ✓ DATABASE_URL           필수
    ✓ REALTIME_BUS           선택
    ✓ REDIS_URL              선택
    ✓ PORT                   선택
    ✓ SHUTDOWN_TIMEOUT_MS    선택

  현재 환경으로 검증
    통과 {"DATABASE_URL":"postgres://***@localhost:5433/app","REALTIME_BUS":"memory",…}

  설정 이상 없음
포트를 바꿀 땐 두 쌍을 함께 바꾼다 — DB_PORT↔DATABASE_URL의 포트, BROKER_PORT↔REDIS_URL의 포트. 하나만 바꾸면 컨테이너는 새 포트로 뜨는데 앱은 옛 포트로 붙어 다른 DB에 조용히 연결된다 — 에러가 아니라 잘못된 성공이라 더 위험하다. make env-check가 이 짝을 검사한다.
.env는 이미지에 들어가지 않는다(.dockerignore + 빌드 단계에서 제거). 빌드는 설정 없이도 돌아가고(검증은 지연 실행), 컨테이너 설정은 오직 실행 시 환경변수로만 들어온다 — 같은 이미지를 개발·스테이징·운영에 그대로 올릴 수 있어야 하기 때문이다.
필수 설정이 없으면 앱은 뜨지 않는다. 조용히 떠서 첫 요청에 500을 내는 것이 가장 나쁜 실패 모드이기 때문이다. 이미지에도 같은 규칙이 걸려 있고 make contract가 그것을 검사한다.

8. runtime contract과 검증

이 템플릿의 산출 경계는 이미지 + 아래 convention까지다. 인프라(k8s·CI 플랫폼)는 프로젝트마다 따로 관리한다.

항목약속
실행 사용자non-root
포트frontend 3000 (HTTP + WS 동일 포트) · backend 3001 (호스트에 노출하지 않는다)
설정환경변수만 — 누락 시 부팅 실패하고 누락 항목을 알린다
상태로컬 디스크에 쓰지 않는다(스케일 아웃 가능)
마이그레이션앱 부팅과 분리된 one-shot 실행
헬스/api/healthz(살아있음) · /api/readyz(DB 연결 확인)
종료SIGTERM → 실시간 연결을 1001로 닫고 정해진 시간 안에 종료
make verify    # lint + 타입 + 유닛 테스트 — 커밋 전에 도는 것
make smoke     # 헬스 4 + unary·스트리밍·WS 8 = 12종 — 서버가 떠 있어야 함
make contract  # 두 이미지(frontend·backend)가 위 표를 지키는지
make ci        # 위 전부 + 마이그레이션 + 이미지 빌드 — 러너에서도 이 한 줄

scripts/ci.sh는 플랫폼 중립이다. GitHub Actions든 GitLab CI든 Jenkins든 이 한 줄을 부르면 된다 — CI 플랫폼을 템플릿이 정하지 않기로 했기 때문이다.

9. 자주 막히는 곳

증상원인과 해결
TypeScript … does not provide the compiler API 최신 typescript@7은 Go 포팅판이라 Next 16이 요구하는 JS 컴파일러 API가 없다. 5.x에 핀한다(6은 아직 beta).
컨테이너에서 Cannot find package 'postgres' / 'ws' / 'ioredis' Next 파일 트레이싱은 app/ 코드만 따라간다. 빌드 밖 entry point(server.mjs·migrate.mjs)의 의존은 Dockerfile이 명시 복사한다. 의존이 늘면 node scripts/runtime-deps.mjs로 목록을 다시 뽑아 맞춘다.
컨테이너에서 Cannot find module 'next/dist/compiled/webpack/…' 커스텀 서버가 next()를 부르면 설정 로더 경로를 타는데 standalone엔 그게 없다. .next/required-server-files.json의 설정을 주입해 우회한다(server.mjs 상단).
db 컨테이너가 unused mount/volume로 죽는다 PostgreSQL 18부터 데이터 디렉터리 구조가 바뀌었다. 볼륨은 /var/lib/postgresql에 건다(.../data 아님).
포트가 이미 쓰이고 있다 .env의 DB_PORT·BROKER_PORT·WEB_PORT만 바꾸면 된다. compose가 그 값을 읽는다.
같은 idempotency key인데 두 번 반영됐다 idempotency 저장소가 프로세스 메모리다. 인스턴스가 여럿이면 키가 다른 인스턴스로 갈 수 있다. IDEMPOTENCY_STORE=redis로 공유 저장소를 쓰면 된다(도메인 코드는 그대로 · 구현은 backend/internal/idempotency에 이미 있다).
lint가 CSS에서 깨진다 Biome 파서가 Tailwind v4의 @theme를 아직 못 읽어 스타일시트는 검사 대상에서 뺐다.
스키마를 고쳤는데 repo.go가 옛 컬럼을 쓴다 make sqlc를 건너뛰었다. 마이그레이션이 schema의 source of truth이므로 sqlc를 다시 돌려야 생성물이 따라온다 — 건너뛰면 빌드가 깨져서 알려 준다.
포트를 바꿨는데 데이터가 안 보인다 DB_PORT만 바꾸고 DATABASE_URL을 안 바꾼 것이다 — 앱이 예전 포트의 다른 DB에 붙었다. make env-check가 잡아 준다.
전부 초기화하고 싶다 make nuke — 볼륨까지 지운다. 다음 기동 때 스키마가 새로 적용된다.
