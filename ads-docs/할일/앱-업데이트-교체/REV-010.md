## SPEC-018 Phase 1 코드 리뷰 — 출시 키 · APK 빌드 · 배포 파이프라인

대상은 SPEC-018 Phase 1에서 바뀐 코드다.

- 새 파일: `src/scripts/android-release-key.sh` · `src/scripts/build-android-release.sh` · `src/mobile/release.json` · `src/mobile/release-cert.json` · `src/frontend/e2e/app-distribution.spec.ts`
- 바뀐 파일: `src/scripts/deploy-h2500-3.sh` · `src/mobile/android/app/build.gradle` · `src/frontend/sw/sw.template.js` · `src/frontend/next.config.ts` · `src/.gitignore`

검토자들은 실제 셸(bash 3.2·macOS sort)에서 확인했고, 로컬 운영 빌드(3220)에 curl로 재현했다.

### 핵심 지적

- **같은 versionCode 보호가 이 맥의 캐시에만 있었다**(운영 H-1). 다른 맥에서 배포하거나 캐시를 지우면 같은 번호로 다른 바이트가 나갈 수 있었다.

→ 사이트 android.json과 비교한다. 같은 번호에 바이트가 다르면 멈춘다. 경로가 다른 깨끗한 사본 둘에서 빌드해도 바이트가 같았다(sha `d88a57d6…`). 그래서 정상 배포는 이 검사를 통과한다.

- **APK 확인이 실패하면 DEPLOYED_REF가 옛 값으로 남는다**(운영 H-2). 그러면 다음 배포의 스키마 하강 검사가 틀린 기준을 쓴다.

→ 확인을 기록 뒤로 옮겼다. 실패하면 끝에서 0이 아닌 코드로 알린다.

- **키 백업이 안내 두 줄뿐이었다**(보안 H-2).

→ 백업 표식 `~/.liftgram-release/BACKED_UP`에 적힌 지문이 출시 키와 같아야 배포 스크립트가 APK를 낸다.

- **없는 APK 이름의 404 HTML이 APK 헤더를 달고 「.apk」로 저장된다**(웹 M-1 · 3220에서 재현).

→ `src/frontend/server.mjs`가 파일이 없으면 짧은 404(no-store)로 끝낸다.

- **배포 순간 받던 사람이 404를 받는다**(운영 M-5 · 웹 M-2).

→ 직전 버전 APK 한 벌을 같이 싣는다.

- **비밀번호가 환경 변수로 넘어가고, gradle 데몬이 남는다**(보안 M-2 · 운영 M-6).

→ `--ks-pass stdin`과 `--no-daemon`을 쓴다. 기본 경로를 읽던 옛 signingConfigs는 명시적 환경 변수일 때만 읽는다(보안 M-3).
