## 핵심 의견
1. **설계 뼈대는 단단하다.** 다음은 코드와 실측으로 확인했다.
   - `status='writing'` 묶음, 부팅 정리, 동기 멈춤(`pauseSync` 가 진행 중 동기를 기다림), 쓰기 안에서 id·삭제 표시 재판정.
   - created 행의 영구 삭제와 삭제 표시 구분, flush 상한 5초.
   - markLocalWins 는 별칭 `exercise_id`, 그리고 사람이 이름을 바꾼 커스텀 `name_ko` 에만 쓴다(ADR-042 개정 범위 안).
   - 피드·PR·완료 요약 경로를 부르지 않는다. D-12 칸 값 계약(plan.ts 머리 주석 = 코드)도 지켜진다.
   - 원본 CSV 는 콘솔·오류 보고·sessionStorage·네트워크 어디에도 실리지 않는다. 오류는 코드 문자열뿐이고, 오류 보고기도 없다.
2. **가장 큰 구멍은 탭이 두 개일 때다(P5-1, 실측 재현).**
   - LokiJS 증분 IndexedDB 어댑터는 다른 탭이 디스크를 바꾼 것을 보면 자기 메모리 사본으로 **DB 전체를 덮어쓴다**.
   - 가져오기를 끝낸 뒤 이미 열려 있던 다른 탭에서 「빠른 시작」을 한 번 누르면, 디스크의 가져온 행이 전부 0이 됐다.
   - 앱 전체에 원래 있던 위험이다. 하지만 가져오기가 1만 세트 규모로 키운다. 또 「진행 중 운동」 검사와 부팅 정리가 다른 탭을 보지 못하는 새 경로도 생긴다.
3. **결정적 id 의 하위 순번이 사람의 결정에 따라 밀린다(P5-3).**
   - 같은 파일을 두 기기가 다른 결정으로 가져오면 종목 줄과 세트가 섞인다.
   - core 는 운영에 있지만 화면이 없어 아직 아무도 가져오지 못했다. **id 규칙을 바꿀 마지막 기회가 이번 화면 배포 전**이다.
4. 구현자가 남긴 위험 ②③(되돌리기 삭제 표시가 새 행을 지움, 1.1초 대기)은 **pull 쪽 필터 하나로 같이 풀 수 있다**(P5-2).
5. 성능(①)은 진행 화면을 조작할 수 없는 단계라 체감 피해가 작다. 1000행 또는 시간 예산 방식으로 줄이는 것을 권하지만 막을 일은 아니다(P5-8).

## 지적

### P5-1 · 높음 · 탭 두 개 — 다른 탭의 자동 저장이 가져온 기록을 디스크에서 통째로 지운다(실측)
- 위치
  - `core/src/db/adapter.ts:36-45`: `onDidOverwrite` 미설정 · 다중 탭 가드 없음
  - `core/src/data/importRepository.ts:120-128`: 준비 판정이 이 탭의 메모리만 본다
  - `importRepository.ts:631-640`: 부팅 정리
- 재현(로그아웃 기기, 같은 브라우저 컨텍스트)
  1. 탭 B 로 `/` 를 열어 둔다.
  2. 탭 A 에서 `/account/import` 로 Hevy kg 표본을 끝까지 가져온다. 디스크 `{workouts:2, set_logs:6, import_batches:1}`.
  3. 탭 B(새로고침 없이)에서 「빠른 시작」을 누른다. 디스크 `{workouts:0, set_logs:0, import_batches:0, 내 운동:1}`.
  - 반대로 A 가 다음에 저장하면 B 의 운동이 사라진다.
- 같은 뿌리에서 나오는 가져오기 전용 경로
  - (a) 가져오는 중에 새 탭을 열면, 그 탭 부팅 정리가 디스크의 `writing` 묶음을 지우고 저장한다.
  - (b) 다른 탭에서 시작한 운동을 `hasActiveWorkout` 이 보지 못한다(U-19 무력화).
  - (c) 다른 탭의 동기는 멈추지 않는다.
- 영향
  - 로그아웃 기기는 영구 손실이다.
  - 로그인 기기는 A 가 이미 push 했으면 다음 pull 로 되살아난다. push 전이면 손실이다.
  - 「가져오기 기록」도 사라지므로 사용자는 지워진 줄도 모른다.
- 수정안
  1. **이번 화면 안**: 가져오기·되돌리기 시작 전에 단일 탭인지 확인한다.
     - `navigator.locks.request("liftgram-import", {ifAvailable:true})` + `BroadcastChannel("liftgram-tabs")` ping(200ms 안에 응답한 탭 수).
     - 다른 탭이 있으면 `import.blocked.other_tab` 「다른 탭에서 열린 리프트그램을 닫은 뒤 가져와 주세요」로 막는다.
     - 진행 중에는 채널로 「가져오는 중」을 알려, 새로 열린 탭은 부팅 정리를 미루고 안내만 한다.
  2. **앱 전체(별도 작업)**: `extraIncrementalIDBOptions.onDidOverwrite` 에서 「다른 탭에서 바뀌었어요 — 새로고침」 배너를 띄우고 쓰기를 막는다. 또는 Web Locks 로 쓰기 탭을 하나로 둔다.

### P5-2 · 중간 · 원격 삭제 표시가 새로 가져온 created 행을 지운다 — 1.1초 대기는 한 경우만 막는다(위험 ②③)
- 위치
  - `importRepository.ts:244-253`: 1.1초 대기 + 재동기
  - Watermelon `sync/impl/applyRemote.js`: 원격 `deleted` 의 id 를 로컬 상태와 상관없이 destroy 한다. 소스로 확인했다.
- 근거
  - 1.1초 대기는 맞다. 서버 `cursorOverlap=1s`(`service.go:41`)이고, `updated_at`·`until` 이 같은 DB `now()` 라서 두 번째 커서가 그 삭제 표시를 넘는다.
  - 하지만 아래 경우는 못 막는다.
    - 다른 기기가 오프라인으로 되돌리고 **나중에** 올리는 경우.
    - 이 기기가 오프라인으로 가져온 뒤 그 삭제 표시를 받는 경우(구현자 ②).
  - 서버 상수와 클라이언트 상수가 테스트 없이 묶여 있다(③).
  - 결과는 묶음 행은 `done · 운동 N개` 인데 운동이 0개다. 소리 없이 일어난다.
- 수정안: pull 적용 전에 필터를 둔다. `syncEngine` 의 `pullChanges` 결과에서 `workouts·workout_exercises·set_logs·exercises·import_aliases` 의 `deleted` 중 id 가 `imp-|cx-|ia-` 이고 **로컬 행이 `_status='created'`** 인 것을 뺀다.
  - created 는 「이 기기가 그 삭제를 알기 전에 새로 쓴 것」이다.
  - 다음 push 가 서버에서 `deleted=false` 로 되살린다. D-17 성질이고 Go 테스트로 고정한다.
  - 다른 기기에도 일관되게 퍼진다.
  - 이 필터가 들어가면 1.1초 대기와 재동기는 지워도 된다(코드 보존 규칙대로 주석 처리).
  - core 단위 테스트: created 행 + 원격 deleted → 남는다 / synced 행 + 원격 deleted → 지워진다.

### P5-3 · 중간 · 하위 id(종목 줄·세트)가 「가져오지 않기」 결정에 따라 밀린다 — 기기 간 섞임

- 재현(사고 실험)

  2. 기기 A 는 전부 가져온다. `we-0`=스쿼트, `we-1`=벤치, `we-2`=데드.

  4. 두 기기가 push 하면 서버는 레코드마다 나중 것이 이긴다. `we-0` 이 벤치가 되고 스쿼트 세트 id(`we-0-j`)가 섞인다. `we-2` 데드는 중복된다.

- 수정안
  - 종목 줄 id 는 **파일 안 원래 순번**(skip 포함, `pw.exercises` 의 index)으로 만든다. 세트 id 는 원래 세트 순번으로 만든다. 그러면 결정이 달라도 같은 id 는 같은 원본 줄을 가리킨다.
  - 화면 배포 전이라 이미 가져온 사용자가 없다. 지금 바꿔야 한다(배포 뒤에 바꾸면 재가져오기 멱등이 깨진다).
  - 테스트: 같은 파일 · 결정 두 벌 → 공통 종목의 id 집합이 같다.

### P5-8 · 낮음 · 가장 긴 long task 588ms(6×) — 묶음 크기(위험 ①)
- 위치: `importRepository.ts:60` `IMPORT_WRITE_MAX_ROWS = 2000`
- 판단
  - 진행 화면은 닫을 수도 조작할 수도 없다. 그래서 체감 피해는 진행 막대 갱신이 끊기는 정도다(펄스 애니메이션은 합성 스레드에서 돈다).

- 권고(택1, 막을 일 아님)
  - (a) 1000행으로 내린다. 묶음 8→16개, 양보 8번 추가로 수십 ms 늘고, long task 는 약 절반이 된다.
  - (b) 시간 예산 방식: 첫 묶음 500행 → 잰 ms/행으로 다음 묶음을 목표 ≈120ms 에 맞춘다. 상한 2000, 하한 200. 저사양 폰에 가장 맞는다.
- 더 큰 long task 는 따로 있다: **다른 기기의 첫 pull 이 1.6만 행을 batch 하나로 적용**하는 것(D-14). 백로그에 이어 둔다.

### P5-11 · 낮음 · 두 기기 동시 가져오기 → 묶음 소유권이 뒤바뀐다
- 위치: `plan.ts:338`(`import_batch_id` 가 레코드마다 나중 것이 이김) · `importRepository.ts:481`(되돌리기는 `import_batch_id` 로 모은다)
- 영향
  - 같은 파일을 A·B 가 각자 가져와 둘 다 push 하면, 운동 행의 `import_batch_id` 는 나중에 올린 쪽 묶음이 된다.
  - 먼저 올린 쪽에서 되돌리면 0개를 지우고도 「되돌림」으로 표시된다. 지울 것을 못 지울 뿐이라 데이터 손실은 없다.
- 수정안
  - 되돌리기 결과가 0개인데 묶음 `workout_count>0` 이면 「다른 기기에서 다시 가져온 기록이에요 — 그 기기의 기록에서 되돌려 주세요」 같은 안내를 보인다.
  - 묶음을 undone 으로 바꾸기 전에 확인한다.

### P5-12 · 정보 · 되돌리기 경고는 무게·횟수 고침(user_edited)만 센다
- 위치: `importRepository.ts:514`
- 내용: 가져온 운동의 이름 바꾸기(`renameWorkout`)나 RPE·RIR 고침은 경고 없이 같이 지워진다. 문구 「앱에서 직접 적은 기록은 그대로예요」는 사실이다(새 운동은 안 지운다). 그대로 두되 알고 있을 것.

### P5-13 · 정보 · 개인정보 확인 결과
- 통과한 것
  - 원본 CSV 본문은 sessionStorage·콘솔·오류 보고·네트워크에 실리지 않는다. 계산 오류는 코드만 돌려준다.
  - `file_label` 은 확장자를 뺀 40자로 서버에 동기된다(D-16 수용).
  - 코칭 기록(`records.go:8,67` · `report.go:29`)은 `import_batches·import_aliases` 를 넣지 않는다.
- 알아 둘 것
  - 임시 저장 `liftgram.importDraft` 에는 **원본 종목 이름**과 사람이 친 커스텀 이름이 들어간다. 「결정표」의 일부라 탭 범위로 허용할 만하다. 나가기·완료·새로고침 뒤 같은 파일이면 쓰이고, 확인을 받고 나가면 지워진다.
  - 가져온 운동 이름·메모는 사용자 기록으로 서버에 동기된다. 코칭 권한이 있으면 트레이너도 볼 수 있다(의도된 동작).

### 위험 ⑤(번들러 Worker) 평가 — 지적 없음
- 전역 `Worker` 는 생성 순간에만 동기적으로 바꾸고 `finally` 에서 되돌린다. 경합이 없다.
- 부트스트랩이 깨져도 `error` 이벤트나 15초 침묵 뒤 메인 대체로 떨어진다. 기능은 잃지 않는다.
- `data-import-via` 를 검사하는 e2e(서비스워커 켠 셸)를 Next 올릴 때 회귀 감시로 두면 충분하다.
