## 핵심 의견

1. **집계 정확성은 ADR-039대로 맞다.** 근거:
   - `setsByMuscle` 하나로 센다(주근육 1 · 보조근 0.5 · 주·보조가 겹치면 주 1 · fullBody는 따로 · other는 제외).
   - 워밍업은 `is_warmup`과 처방 `warmup` 둘 다로 뺀다. 유산소는 저장소에서 뺀다.
   - 루틴 계획 세트는 처방이 있으면 처방에서 워밍업을 뺀 줄 수, 없으면 target_sets다. 세션은 `done !== false`면 끝낸 세트, 그 운동의 세트 전부가 계획이다(프리레이 세트는 `done=false`로 만들어지므로 맞다).
   - 실측: 벤치 3 + 스쿼트 3 루틴에서 시트에 가슴 1/3 · 어깨·삼두 0.5/1.5 · 대퇴 0/3 · 햄·둔 0/1.5가 나왔다. 통계 카드는 가슴 1 · 대퇴 1 · 보조 0.5×4였다.
   - 남는 쟁점은 **실패 세트를 어떻게 세느냐** 하나다(P2-1).
2. **기존 「근육군 분포」를 대체해도 통계 숫자는 회귀하지 않는다.** StatsClient에서는 분포 조회·state·렌더만 주석으로 막았다. 개요·전 기간 비교·추세·PR 조회는 그대로다. 「근육군 분포」 글자 0개, 근육 섹션 1개도 확인했다. 다만 볼륨 kg 보조 숫자는 정의가 세트 수와 다르다(P2-4).
3. **빨강 규칙은 지켰다.** 그림은 무채 농도로 칠하고, 선택한 근육만 brand-vivid다. 그래서 M-2(오늘 카드 「시작」 = 빨강 채움)와 같이 있어도 홈의 빨강 종류는 늘지 않는다. 360 라이트·다크에서 켬과 끔의 빨강 집합을 재 보니 같았다(brand 테두리·라벨·시작 채움 + 로고 vivid). 통계에서 줄을 선택해도 brand-vivid(선택)와 brand(탭·추세 막대) 2종이다.
4. **가장 눈에 띄는 UX 비용은 오늘 카드다.** 360에서 루틴 이름 폭이 177px → 123px로 줄었다(그림 44px + 여백). 카드 높이도 79px → 102px(+23px)로 늘었다. 이름이 「아주긴이름의…」처럼 6자 남짓에서 잘린다(P2-2).
5. **설정은 바로 반영되고 동기된다.** `setPref` 경로를 그대로 써서 키별 쓰기 대기 표식과 PREFS_EVENT가 적용된다. 운동 화면을 연 채 다른 탭에서 끄면 「오늘 근육」 버튼이 0개, 다시 켜면 1개가 됐다. 끈 상태 좌표는 기준선과 같다(rir 100/36 · 첫 세트 281).
6. **성능은 위험하지 않다.** 루틴 카드 그림은 오늘·추천 카드 두 장에만 붙는다(목록 줄 제외). 두 조각이 조회를 2초 공유 캐시로 나눠 쓰므로 루틴 수십 개여도 조회는 1~2건이다. 운동 중 시트는 열 때 한 번만 읽는다. 통계는 같은 「완료 세트 전체」 조회를 한 화면에서 여러 번 하는 중복이 있다(P2-5).

### P2-1 (중간) 실패 세트를 근육 세트로 센다
- 위치: `src/core/src/data/muscleLoadRepository.ts:143-151`(periodMuscleLoad) · `:119-127`(sessionMuscleLoad). P1 `periodSummary.ts:403`도 같다.
- 현상: 근육 집계는 워밍업과 `done=false`만 뺀다. 그런데 앱의 「작업 세트」(`isWorkingSet` = 워밍업도 실패도 아님)와 개요 KPI `workingSets`, 볼륨은 실패 세트를 뺀다.
- 재현: 벤치 1세트를 실패로 표시하고 운동을 마친다 → 통계 근육 균형에 「가슴 1세트」가 나오고 볼륨 칸은 빈다. 같은 화면 KPI 작업 세트는 0이다.
- 영향: ADR-039 문구 「완료한 작업 세트」와 앱의 용어 정의가 어긋난다. 회원 리포트·성과 요약(같은 함수)에서 트레이너가 숫자를 맞춰 볼 때 차이가 난다.
- 수정안: 어느 쪽이든 정해서 한 곳에 적는다. ① `MuscleLoadItem`에 `isFailed`를 넣고 `setsByMuscle`이 뺀다(권장 — 「작업 세트」 정의와 맞춤, 세 호출부에 `isFailed` 전달). ② 실패 세트도 자극으로 세기로 했다면 ADR-039에 「실패 세트 포함」을 명시하고 halfNote 근처에 적는다. 어느 쪽이든 domain 테스트 1건을 추가한다.

### P2-6 (낮음) 첫 진입 때 `?muscle=`을 지웠다가 다시 쓴다 · 카탈로그를 두 번 조회한다
- 위치: `src/frontend/lib/muscleQuery.ts:25-49`
- 현상: 첫 효과가 `applied.current = true`를 **같은 커밋 안에서** 먼저 세운다. 그래서 「처음 적용 전에는 쓰지 않는다」 가드가 통하지 않는다. 둘째 효과는 아직 `muscle=""`인 상태로 돌아 쿼리를 지운다.
- 재현(탐침): 통계 「안 한 근육」 칩 → 카탈로그. `history.replaceState` 기록이 `["/exercises", "/exercises?muscle=back"]`로 남았다. 최종 주소와 눌린 칩은 맞다.
- 영향: 결과는 맞지만, 순간적으로 쿼리 없는 주소가 된다(Next 라우터의 searchParams 동기·분석 로그에 잡힐 수 있다). 첫 렌더가 필터 없는 전체 카탈로그를 한 번 조회한 뒤 부위 필터로 다시 조회한다.
- 수정안: 둘째 효과에서 첫 실행을 건너뛴다(`const first = useRef(true); if (first.current) { first.current = false; return; }`). 또는 `useState`의 lazy 초기값으로 쿼리를 읽는다. 클라이언트 전용이니 하이드레이션 차이를 확인해야 하고, 지금처럼 효과 방식을 유지해도 된다.

### P2-7 (낮음) i18n 문구
- 위치: `src/core/src/i18n/locales/ko.ts:1122`·`:1130`·`:1121`
- 「아직 센 근육이 없어요」·「이 기간에 센 근육이 없어요」: 「센」이 「세다(count)」가 아니라 「힘센」으로 읽힌다. 웰니스 화면에서 「센 근육 없음」은 평가처럼 들릴 수 있다. → 「아직 기록된 근육이 없어요」·「이 기간에 기록된 근육이 없어요」.
- `ariaSummary` 「많이 한 근육: …」은 0.5세트까지 전부 읽으므로 「많이 한」과 안 맞는다. → 「한 근육: {list}」(en 「Muscles worked」와 같은 뜻).
- 나머지 키(ko·en 20개 대칭, `muscleMap.` 게이트 접두사)와 평가·권고 표현 없음은 확인했다.

### P2-8 (낮음) 줄의 aria-pressed가 스크린리더 사용자에게는 효과가 없다
- 위치: `MuscleBalanceCard.tsx:146-156` · `session/TodayMuscleSheet.tsx:112-119`

- 포커스 링(브라우저 기본 auto)은 줄·‹ ›·「오늘 근육」 모두 보였다. 시트를 닫으면 버튼으로 포커스가 돌아오는 것도 확인했다.
