## 총평

**조건부 통과.** P4의 화면 수정 9건은 의도대로 들어갔다. 대비 계산도 모두 4.5:1을 넘고, 삭제의 위험 표시는 확인창(`destructive`)이 맡아 준다. 다만 아래 두 가지가 남아 있다.

1. 「빨강 채움 화면당 1개」 규칙이 홈의 **가장 흔한 경로 셋(폴더·오늘 카드·추천 카드)**에는 적용되지 않았다. 측정 e2e도 그 경로를 재지 않는다.
2. 세션 이상은 테스트 환경 탓이 아니다. **실사용에서도 생기는 refresh 회전 경쟁 버그**로 판정했다(H-1). 이번 커밋(UI)이 만든 회귀는 아니므로 P4 배포를 막을 사유는 아니다. 그러나 별도 픽스로 반드시 다뤄야 한다.

## 높음

### H-1 refresh 회전에 유예가 없다 — 응답을 못 받은 갱신 하나가 세션 전체를 죽인다 (실사용 버그)

- **위치**
  - `src/backend/internal/auth/service.go:189-208`: `Refresh`가 옛 토큰을 즉시 폐기한다. 재사용 유예 창이 없다.
  - `src/frontend/app/api/session/refresh/route.ts:42-44`: backend가 401이면 **쿠키를 무조건 지운다**(`Max-Age=0`).
  - `src/frontend/lib/session.ts:220-252`: `refreshOnce`가 401을 받으면 깃발을 내려 로그아웃 상태가 된다. 단일 비행은 **한 문서(JS 실행 환경) 안에서만** 보장된다.
  - `src/frontend/app/components/AuthProvider.tsx:98-121`: 문서를 새로 열 때마다 `load()`가 `restoreSession()`, 즉 refresh를 부른다(access는 메모리에만 있다).
- **기전**
  1. 문서 A가 `/api/session/refresh`를 보낸다.
  2. 응답이 오기 전에 문서가 사라진다(전체 페이지 이동·새로고침·앱 종료·탭 닫기). 브라우저는 요청을 끊는다.
  3. Next 라우트 핸들러는 클라이언트가 끊겨도 backend `Refresh`를 끝까지 호출한다(`req.signal`을 넘기지 않는다). 그래서 **옛 refresh는 폐기되고, 새 refresh를 담은 Set-Cookie는 버려진다.**
  4. 브라우저에는 폐기된 옛 쿠키가 남는다. 다음 문서의 refresh는 401을 받고, 라우트는 쿠키를 지우고, 화면은 로그아웃된다.
  - **두 탭(또는 PWA와 브라우저 탭)**에서도 같은 일이 난다. 두 문서가 같은 쿠키로 동시에 갱신하면 한쪽만 이긴다. 진 쪽의 401 응답이 늦게 도착하면 **이긴 쪽이 막 구운 새 쿠키까지 `Max-Age=0`으로 지운다.** 그러면 모든 탭이 로그아웃된다.
- **e2e에서 본 현상과의 대응**
  - `e2e/declutter-shots.spec.ts`의 첫 P4 테스트에는 `await page.goto("/feed");` 바로 다음 줄에 `shot("post-detail", () => page.goto("/feed") …)`가 있다. **기다림 없이 같은 주소로 두 번 연속 이동**하는 것이다.
  - `goto`는 load 이벤트에서 돌아온다. 반면 `load()`의 refresh는 하이드레이션 뒤에 출발하므로 아직 비행 중일 수 있고, 두 번째 `goto`가 그 요청을 끊는다. 이 지점 뒤에 messages, notifications, profile, **account** 순서로 찍힌다.
  - 짧은 흐름(두 번째 「로그인」 캡처 테스트, `declutter-p4.spec.ts`의 `가입`)은 같은 문서 안에서 바로 확인하거나 이동 사이에 1.5초 이상 기다린다. 그래서 재현되지 않는다.
  - 「1.5분」이라는 경과 시간은 원인이 아니다. access TTL은 15분, refresh TTL은 30일이다. 원인은 **이동 타이밍**이다.
- **보조 경로(의심, 중간)**: `AuthProvider.tsx:149,156`의 `signUp`·`logIn`은 `setTokens()`를 **await하지 않는다**(소셜 착지 `:165`만 기다린다). 가입 직후 곧바로 전체 이동하면 `POST /api/session`이 끊긴다. 그러면 쿠키가 아예 없고, 다음 문서에서 로그아웃된다. 테스트는 `auth-email`이 보이자마자 `카탈로그_준비`(`page.goto`)로 넘어가므로 이 경로도 열려 있다. 실사용에서는 그다음이 클라이언트 이동(next/link·LinkInterceptor)이라 드물다.
- **판정**: **실사용 버그.** 다음 상황에서 생긴다.
  - 앱을 연 직후 0.5~1초 안에 당겨서 새로고침하거나 앱을 닫을 때
  - 「새 버전」 띠로 새로고침할 때
  - PWA와 브라우저 탭을 함께 열어 두었을 때
  - 백그라운드 탭 두 개가 동시에 복귀할 때

  e2e는 이 경쟁을 우연히 자주 일으켰을 뿐이다. 서비스워커는 `/api/*`를 건드리지 않으므로(`sw/sw.template.js:98`) 원인이 아니다. syncOwner도 원인이 아니다. 로그아웃을 일으키는 코드 경로는 refresh 401(`session.ts:232`)과 명시적 `logOut`, 둘뿐이다.
- **재현 절차**
  1. 같은 쿠키로 갱신을 두 번 보내 유예가 없음을 확인한다. 로그인한 브라우저의 DevTools에서 다음을 실행한다.
     ```js
     const h={"x-liftgram-session":"1"};
     await Promise.all([fetch("/api/session/refresh",{method:"POST",headers:h}),fetch("/api/session/refresh",{method:"POST",headers:h})]).then(r=>r.map(x=>x.status))
     ```
     하나가 200, 하나가 401이면 유예가 없는 것이다. 이어서 새로고침하면 로그아웃되어 있을 수 있다. 쿠키가 지워졌는지는 응답 도착 순서에 따라 달라진다.
  2. Playwright로 재현한다. 가입한 뒤 1.5초 기다린다. `for (i<5) { await page.goto("/feed"); }`를 기다림 없이 돌린 뒤 `page.goto("/account")`로 가서 `auth-email`이 없는지 본다.
  3. 실기기로 재현한다. 로그인한 PWA를 연 직후 1초 안에 당겨서 새로고침하는 것을 몇 번 반복한다. 네트워크가 느릴수록 재현이 쉽다.
- **수정안**(별도 /spec, Task 등급)
  1. backend: 회전된 옛 토큰에 **짧은 유예(예: 30~60초)**를 준다. 그 안에 옛 토큰이 다시 오면 `replaced_by`가 가리키는 같은 후속 세션을 다시 내주거나 새로 회전시킨다. 업계 표준인 refresh reuse grace다. 유예가 지난 재사용은 계열 전체를 폐기한다(탈취 탐지).
  2. 라우트: 401일 때 쿠키를 지우는 것은 **요청에 실려 온 쿠키 값이 지금도 같을 때만** 의미가 있다. 다른 문서가 이미 바꿨을 수 있다. 차선책으로 401 응답에는 Set-Cookie를 붙이지 않고, 지우는 일은 `DELETE`(로그아웃)에만 맡긴다.
  3. 프론트: 문서 간 단일 비행이 필요하다. `navigator.locks.request("liftgram-refresh", …)` 또는 BroadcastChannel을 쓴다. `signUp`·`logIn`에서 `await setTokens(...)`로 바꾼다.
  4. 회귀 e2e: 위 재현 절차 2를 `session.spec`에 추가한다.

## 중간

### M-1 「빨강 채움 화면당 1개」가 홈의 다른 시작 버튼 셋에는 적용되지 않았다

- **위치**: `src/frontend/app/components/routines/RoutinesClient.tsx`
  - `:834` FolderGroup 안 루틴 「시작」: 기본 primary
  - `:712` TodayCard 「▶ 시작」: primary
  - `:774` RecoCard 「▶ 시작」: primary
- **재현**
  - 루틴을 폴더에 넣고 펼친다. 폴더 안 루틴 수만큼 빨강 채움이 생긴다. 빠른 운동 시작까지 더해 2개 이상이다.
  - 주간 스케줄을 만든다. 오늘 카드 「시작」과 빠른 운동 시작이 둘 다 빨강 채움이다. 추천 카드(RecoCard)도 같다.
- **판단**: V5 수정은 「폴더 밖 루틴 줄」 하나만 바꿨다. 같은 화면의 같은 동작(루틴으로 시작)이 폴더 안에서는 빨강, 밖에서는 회색이 되어 일관성도 깨진다.
- **수정안**
  - 폴더 안 「시작」은 V5와 같이 `variant="secondary" icon="play"`로 맞춘다.
  - 오늘 카드·추천 카드가 있으면 **그 카드를 주 행동으로 삼고 빠른 운동 시작을 secondary로 낮출지**, 반대로 할지 결정한다. 진행 중 막대에서 쓴 방식(P3 M5)과 같은 조건부 변형이다. 이 결정은 스펙에 적는다.
  - e2e 「빨강 채움 1개」를 폴더·스케줄 시나리오로 넓힌다.

### M-2 루틴 시작 동선 약화 — 회색 「시작」은 받아들일 만하나 보완이 필요하다

- **위치**: `RoutinesClient.tsx:880-889`
- **판단**: 캡처(`shots/p4/after/routines-home-390-light.png`)를 보면 회색 상자에 ▶ 아이콘이 있어 버튼으로 읽힌다. 다만 루틴이 있는 사용자의 실제 주 동선은 「루틴으로 시작」인데, 화면에서 가장 강한 빨강이 「빠른 운동 시작」(빈 운동)이 되었다. 루틴 사용자에게는 위계가 거꾸로다.
- **수정안**(제품 결정): 루틴이 1개 이상이면 첫(또는 최근) 루틴의 시작을 주 행동으로 하고 빠른 시작을 보조로 낮추는 안을 검토한다. 최소한 사용자 확인 항목으로 스펙에 올린다.

### M-3 백업 버튼 `min-[420px]:flex-row` + `whitespace-nowrap` — 420~460px에서 넘침 (의심)

- **위치**: `src/frontend/app/components/sync/BackupCard.tsx:61`
- **기전**: 두 버튼은 `fullWidth`(w-full)다. 420px 이상에서 나란히 놓이면 칸 하나가 약 (뷰포트 − 64 − 8)/2 ≈ 174px(420 기준)이다. 반면 「백업 파일 내보내기」에 필요한 폭은 아이콘 18 + 간격 6 + 글자 약 135 + 좌우 패딩 32로 약 190px이다. nowrap 때문에 줄바꿈 대신 **버튼이 카드 밖으로 넘치거나 글자가 잘린다.**
  - 분기 기준이 **뷰포트**라서, 카드 폭이 좁게 고정된 레이아웃(최대폭 컨테이너, 태블릿 분할)에서도 같은 문제가 난다.
  - 영어(`Import from file`)는 더 길다.
- **재현**: 계정 화면에서 뷰포트를 420·430·440px로 바꾸고 `btn-backup-export`의 `scrollWidth > clientWidth`인지, 또는 카드 오른쪽 끝을 넘는지 본다.
- **수정안**
  - 분기를 컨테이너 쿼리(`@container`, 예: `@[400px]:flex-row`)로 바꾸거나, 그냥 늘 세로로 쌓는다(가장 단순하다).
  - e2e에 420·440px과 영어 로캘에서 「넘침 없음」(`el.scrollWidth <= el.clientWidth`, 카드 rect 안에 들어가는지)을 추가한다.

### M-4 측정 e2e가 고친 것의 절반만 고정한다

- **위치**: `src/frontend/e2e/declutter-p4.spec.ts`
  - `:72-75`: 대체(swap) 글자색만 잰다. **슈퍼셋 버튼과 삭제 아이콘 색은 재지 않는다.** 누가 다시 `color="var(--color-bad)"`로 돌려도 통과한다.
  - `:107`: 도우미는 `borderTopColor`만 잰다. 지금은 테두리 폭이 0이라 currentColor가 나온다. **분홍 바탕(`brand-muted`)이나 빨강 글자로 돌아가도 통과한다.**
  - `:125-129`: 로그아웃은 `border`·`width`를 모으기만 하고 **단언하지 않는다**(죽은 코드). 글자색만 본다.
  - `:85-101`: 「빨강 채움 1개」는 폴더·스케줄·추천 카드가 없는 상태만 잰다(M-1).
  - `:131-153`: 백업은 360폭(세로 쌓임)만 재므로 420px 분기 쪽은 재지 않는다(M-3).
- **수정안**
  - 각 대상에 대해 `color`·`backgroundColor`·`borderTopWidth>0 ? borderTopColor` 세 값을 brand·bad 집합과 비교하는 헬퍼(`isAccent(el)`) 하나를 만들어 모두 그것으로 단언한다.
  - 백업은 360·420·440 세 폭에서 「줄 수 1」과 「넘침 없음」을 함께 본다.

## 중점 점검 결과

### 1. `Button variant="quiet"`

| 항목 | 결과 |
|---|---|
| 대비 | 글자 `--color-ink2`. 라이트 #3E4348/#FFFFFF ≈ 10:1, /#F7F7F7 ≈ 9.5:1. 다크 #D8DBDF/#2B2B2B ≈ 11:1. **통과** |
| 포커스 | 공용 `focus-visible:outline-2 outline-(--color-brand) offset-2`를 그대로 쓴다. brand와 카드 바탕의 대비는 3:1 이상이다. **통과** |
| 비활성 | `opacity-45`. WCAG에서 비활성 컨트롤은 예외다. 다른 변형과 같은 규칙이다. **통과** |
| 탭 목표 | sm 36px. **미달**(L-1, 기존과 같음) |
| 기존 variant 회귀 | `palette()`는 case만 추가했고 기존 4개 분기는 바뀌지 않았다. 타입 유니온 확장뿐이다. **회귀 없음** |
| 기타 사용처 변경 | 로그아웃 danger→secondary, 루틴 「시작」 primary→secondary, 편집 행 ghost→quiet. 모두 의도된 변경이다. |

도우미 칩(ink2/#F1F2F4 ≈ 9:1)과 PR 금색 글자(라이트 #A16207/흰 바탕 ≈ 4.9:1, 다크 #FFD23F/#2B2B2B ≈ 10:1)도 통과다. 다만 PR 금색이 surface-alt(#F1F2F4) 위에 놓이면 약 4.4:1로 미달할 수 있다. 지금 기록 목록·달력 줄은 카드(흰) 바탕이라 해당하지 않는다.

### 2. 주 행동 1개 규칙의 부작용

- **홈 루틴 「시작」 회색화**: 동선은 살아 있다(▶ 아이콘과 상자가 있다). 위계와 범위는 M-1·M-2를 본다.
- **루틴 편집 삭제 회색화**: 위험 표시는 확인창(destructive)으로 옮겨 갔고 데이터 보호는 유지된다(L-4). 슈퍼셋 칩의 빨강은 남았다(L-3).
- **로그아웃 회색화**: 타당하다. `onLoggedOut()`은 동기 차단만 풀고 기기 기록을 지우지 않는다(`lib/syncTransport.ts:136-138`). 「데이터를 지우지 않는 일상 행동」이라는 근거가 코드로 확인된다. 기기 기록 폐기(`resolveConflictByDiscard`)는 AccountGuard에 따로 있다.
