## 판정

**배포 가능.** 높음 0건 · 중간 1건 · 낮음 7건.

- 기본 설정(`MIN_CLIENT_VERSION` 빈 값)에서는 사용자 요구 5가지를 모두 지킨다. 실측 결과: 사용 중 저절로 새로고침 0회, 버튼을 누르면 새 빌드가 뜸, 다른 탭이 적용해도 이 탭은 그대로, 15초 뒤 실패 화면.

## 위험 항목별 확인

1. **사용 중 저절로 새로고침 0**(통과)
   - 새로고침을 일으키는 코드는 `appUpdate.ts:188 reloadOnce` 한 곳뿐이다. 호출하는 조건은 셋이다: `applying` 일 때 오는 controllerchange, 누른 업데이트 중 워커가 activated, 「다른 곳에서 이미 활성화」 상태에서 사람이 누름.
   - 첫 설치와 clients.claim 은 `ignore`, 다른 탭 적용과 늦은 브라우저 활성화는 `mark` 다(P1 실측).
   - 실패하거나 닫으면 `applying=false` 가 된다(:219 · :314). 15초가 지난 뒤 늦게 활성화돼도 새로고침하지 않는다.
   - 다른 `location.reload` 호출(가져오기·ImportElsewhere·ActiveWorkout 오류·schemaGuard)은 모두 사람이 누르는 버튼이다.
   - 반대 방향(누르면 새 빌드가 뜨는가)도 통과. skipWaiting 은 다른 탭이 있어도 활성화하므로 「다른 탭 때문에 못 넘어가는」 경우는 없다. 새로고침한 문서는 새 워커가 처리한다: SWR 셸은 새 워커의 PAGES(설치 때 `cache:"reload"`)에서, 조각은 해시 이름으로 받는다. E3·P1에서 새 build 를 확인했다.
   - 첫 설치(문서가 제어받지 않던 경우)에서 누르면 controllerchange 가 `ignore` 다. 그래도 `statechange → activated` 대비(:305)가 새로고침해 준다. 코드로 확인.
2. **크롬 함정**: 재현됐다. 구현자 진단(부팅 직후)은 맞지만 원인 설명과 회피 방법에 빈틈이 있다. M-1 참조.
3. **덮개**: 클릭·Tab·탭 바는 `inert` 로 막힌다(E3b). 15초 → 실패 → 다시 시도/닫기 상태 기계도 맞다(E6). 표식이 남아도 정적 스크립트(15초 자해제)와 `finishBootCover` 가 무조건 내리므로 영원히 덮이지 않는다(P3). 뒤로 가기는 막지 못한다(L-4).
4. **운동 중 판정과 필수 업데이트**
   - 셸 상태(`activeLoaded`·`activeWorkoutId`)로 버튼을 끄고, 누른 순간 기기 DB 를 다시 본다(:272). 확인에 실패하면 업데이트하지 않는다.
   - 필수 업데이트는 운동 중·`/workout`·셸 판단 전이면 `wait` 다(E7 확인).
   - `compareVersions` 는 앞 세 자리 숫자를 비교한다(0.9<0.10 단위 테스트 있음). 빈 값·잘못된 값·서버 버전 모름·서버 버전 < 최소이면 필수가 아니다(fail-open). 오프라인이나 `/app-version` 오류면 상태를 바꾸지 않는다.
   - `server.mjs` 가 읽는 `./package.json` 은 standalone 런타임 이미지에도 있다(`.next/standalone/frontend/package.json` 확인).
5. **전환기**
   - 메시지 이름 `"skip-waiting"`·`"clear-media"` 는 그대로다. 새로 생긴 `{type:"version"}` 은 옛 워커가 무시하고, 화면은 1초 뒤 null 로 넘어가므로 호환된다.
   - `build-sw.mjs` 는 자리표시자 3개를 검사하고 각각 한 번만 치환한다. 템플릿의 자리표시자도 코드 3곳뿐이다.
   - 기존 기기(v0.47 번들)는 옛 규칙으로 **한 번 더** 저절로 업데이트된다. 운동 화면 밖이면 자동 적용(새로고침 1회)이고, 운동 중이거나 `/workout` 이면 떠날 때 적용된다(옛 SRS-084 보류가 있어 요약은 보호됨). 피할 수 없는 단 한 번이며 보고서 R1에 적혀 있다. 운영 확인 때 사용자에게 미리 알릴 것(L-7).
   - v0.47 워커 아래에서 네트워크 우선 경로로 v0.48 문서가 열리는 경우도 있다. 이때도 컨트롤러 버전이 null 이고 부팅 표식의 `fromBuild` 도 null 이라, 실패 오판 없이 정상 동작한다.
6. **UI**
   - 탭 점은 `--color-ink2` 6px · `aria-hidden` 이고, 링크 안 `sr-only` 「새 버전 있음」 으로 접근 이름이 「프로필 · 새 버전 있음」 이 된다.
   - 「업데이트」 버튼은 회색 상자 `min-h-[44px]`, 덮개의 「다시 시도」는 화면의 유일한 빨강 채움 `min-h-11`(44px), 「닫기」는 회색이다. 빨강·금색 남용이 없다.
   - 라이트와 다크 스크린샷 12장을 확인했고 대비에 문제가 없다. 버전 이중 표기는 L-5.
7. **테스트**
   - 진짜 워커를 쓰는 E1~E8 은 구현자 보고상 수정 전 코드에서 8/8 실패했다. 회귀를 잡는 테스트다.
   - `#64` 기대 변경(「홈 가면 적용」 → 「홈에서도 없음 · 프로필 버튼으로만」)은 사용자 확정 요구와 정확히 일치하므로 타당하다. 첫 테스트 제목만 옛 문장으로 남아 있다(L-6).
   - 빈칸: 다른 탭 시나리오(P1)와 부팅 직후 멈춤(M-1)을 다루는 e2e 가 없다.

## 발견 사항

### 높음

없음.

### 중간

#### M-1 크롬: load 직후 보낸 skip-waiting 은 영영 활성화되지 않고, 그 뒤 그 탭의 새로고침까지 멈춘다. 3초 회피는 원인을 덮을 뿐이고 복구 경로가 없다

- **위치**
  - `src/frontend/lib/appUpdate.ts:232`(`BOOT_SETTLE_MS`)
  - `:301-308`(`settle = BOOT_SETTLE_MS - performance.now()` 뒤 `postMessage("skip-waiting")`)
  - `:309`(멈췄을 때 대책 없음)
  - `lib/i18n.ts:64`(`failedHint` 「잠시 뒤 다시 시도」)
- **재현**
  - 로컬 운영 빌드에서 waiting 워커가 있는 상태로 `page.goto("/")` 한 뒤, 곧바로(약 45ms) `reg.waiting.postMessage("skip-waiting")` 를 보내면 10/10 `installed` 에 멈춘다(경로 무관). 300ms 이상 지나서 보내면 12/12 정상이었다.
  - 멈춘 뒤 다시 보내도, `reg.update()` 를 불러도 풀리지 않는다. **그 탭에서 새로고침하면 20초 넘게 끝나지 않는다.**
  - 같은 출처의 iframe 이나 새 탭을 열면 곧바로 활성화된다. 크로미움이 「대기 워커 활성화 재시도」를 놓치는 것으로 보이며, 새 클라이언트의 내비게이션이 재시도를 일으킨다.
- **왜 중간인가**
  - ① 3초는 `performance.now()` 기준이라 **내비게이션 시작부터** 잰다. 느린 폰이나 느린 망에서 load·하이드레이션·`/app-version` 이 3초 가까이 걸리면, 부팅 직후 시작하는 필수 업데이트는 「load 직후」에 보내게 된다.
  - ② 멈추면 15초 뒤 실패 화면이 뜬다. 「다시 시도」는 같은 메시지를 다시 보낼 뿐이라 반드시 또 실패하고, 사람이 닫은 뒤 당겨서 새로고침하면 **탭이 멈춘 것처럼 보인다**(앱을 강제 종료해야 한다).
  - ③ 수동 버튼도 원리상 같은 조건(옛 워커가 처리 중인 요청이 있는 순간)이면 걸릴 수 있다.
  - ④ 삼성 인터넷도 크로미움 기반이라 같은 동작일 가능성이 높다. iOS 사파리는 WebKit 이라 이 버그와 무관할 것으로 보이지만 실기기 확인은 하지 않았다(보고서 R6·R7).
- **권장 수정**(작고 국소적)
  1. skip-waiting 을 보낸 뒤 약 1.5초 안에 `activating`/`activated` 가 되지 않으면, 숨은 같은 출처 iframe(`/offline` · 미리 받은 셸)을 붙였다 떼어 활성화 재시도를 일으킨다(실측 2/2 해제). 「다시 시도」도 이 단계를 거치게 한다.
  2. 대기 기준을 `performance.now()` 3초에서 「`load` 이벤트 + 짧은 여유(예: 500ms~1초)」로 바꾸거나 둘 다 만족하게 한다.
  3. 실패 문구에 「앱을 완전히 닫았다 다시 열면 적용돼요」를 덧붙인다(시간 초과이고 waiting 이 그대로일 때).
  4. e2e 를 추가한다: 부팅 직후 필수 업데이트에서 load 직후 보내도 활성화되는지.
- 같은 함정이 기존 `lib/schemaGuard.ts:86-90 reloadToNewVersion` 에도 있다. skip-waiting 직후 곧바로 reload 하는데, 그 순간 멈추면 새로고침이 걸린다. 사람이 누르는 드문 경로이고 이번 변경 범위 밖이지만 같은 방식으로 함께 고치기를 권한다.

### 낮음

- **L-1 필수 업데이트 「닫기」가 문서 수명 내내 유지된다(스펙과 다름).** `appUpdate.ts:42·315 dismissed`

  - 권장: visibilitychange 에서 visible 이 될 때 `dismissed` 를 풀거나, 스펙 문구를 「다음 부팅에」로 고친다.
- **L-2 필수 업데이트가 운동 외 작성 중 화면을 날릴 수 있다.** `ServiceWorker.tsx:229-243`
  - 루틴 편집이나 피드 작성 중에 앱으로 돌아오면(visibility → `/app-version`) 덮개가 뜨고 새로고침된다. 저장하지 않은 입력은 사라진다.
  - 기본은 꺼짐이고 「필수」의 성격상 수용 가능하다. 켤 때는 운영 메모에 적어 둘 것.

  - 덮개를 연 순간의 body 자식만 inert 로 만든다. 이후 생기는 포털(토스트 등)은 덮개(z 900) 아래라 클릭은 막히지만 Tab 초점은 받을 수 있다.

  - 권장: 꼬리는 빌드 표시만 남기거나 새 줄 부제로 합친다.
- **L-6 `e2e/feedback-62-64.spec.ts:61` 테스트 제목이 옛 기대로 남아 있다.** 제목은 「…홈으로 가면 적용한다」인데 본문은 「홈에서도 새로고침 없음」을 검사한다. 제목만 고치면 된다.
- **L-7 전환기 한 번의 자동 업데이트(보고서 R1)는 릴리스 메모와 사용자 안내에 명시할 것.** 「이번 한 번만 옛 방식으로 저절로 새로고침되고, 그 뒤로는 프로필 버튼」.
  - 부가 메모: 부팅 덮개 문구는 서버 렌더 `tw()` 라 영어 사용자에게도 한국어로 나온다(`layout.tsx`). 1초 미만 노출이라 사소하다.
