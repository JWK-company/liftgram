## M-1 · `homeReady` 가 사용자(스케줄) 로딩을 기다리지 않음 → 판단 뒤 카드가 버튼 위로 끼어든다

- 근거
  - `RoutinesClient.tsx:73` — `weeklySchedule` 는 `useUser()` 에서 온다. `src/core/src/state/userContext.tsx:29-44` 에서 `base` 는 처음에 null 이고 `getOrCreateLocalUser()` 가 끝나야 채워진다. `loading` 플래그도 있지만 홈은 쓰지 않는다.
  - `RoutinesClient.tsx:286-292` — `(!weeklySchedule || doneLoaded)`. 스케줄이 **아직 null** 이면 「스케줄 없음」으로 보고 바로 통과한다. 읽기 전의 null 과 진짜 「없음」을 가르지 못한다. 같은 함정을 `activeLoaded`·`routinesLoaded` 에서는 이미 막았다(SRS-072 /qa H-2). 스케줄에는 그 장치가 없다.
- 실패 시나리오
  1. 사용자 레코드가 추천보다 늦게 온다. 콜드 스타트에서 IndexedDB 읽기 순서가 바뀌거나, 로그인 직후 동기가 원격 `weeklySchedule` 을 내려받거나, 다른 기기에서 스케줄을 바꾼 뒤 pull 하는 경우다.
  2. `homeReady=true` 이고 스케줄은 없다. 그래서 빠른 시작이 **enabled** 가 되고, 스켈레톤은 걷히고, 추천 카드는 버튼 **아래**에 그려진다.
  3. 그 뒤 스케줄이 도착한다. `todayGuide()`(오늘 카드)와 `CatchUpCard` 가 버튼 줄 **위**에 새로 생긴다(`:419`, `:427-438`). 버튼 줄이 카드 두 장만큼 내려간다.
  4. 빠른 시작은 오른쪽 절반에 있다. 그 자리에 오면 오늘 카드의 「시작」(`btn-start-today`)이나 놓친 루틴의 「이걸로 시작」(`btn-catchup-start`)이 놓인다. 둘 다 카드 오른쪽 끝이다. 사용자는 엉뚱한 루틴으로 운동을 시작하게 된다.
  5. 빨강 채움도 바뀐다. 「빠른 시작」 또는 추천에서 「오늘 시작」으로 옮겨 가므로 SRS-072 의 깜빡임 의도와도 어긋난다.
- 비고: 오늘 카드 부분은 v0.54.0 에도 있던 위험이다. 이번 변경으로 놓친 루틴 카드까지 버튼 위로 올라와 밀림 폭이 커졌다. 「판단 뒤 밀림 없음」이라는 이번 변경의 핵심 주장이 깨지는 경로다.
- 권고: `useUser()` 의 `loading` 을 받아 `homeReady` 에 `!userLoading` 을 더한다. 원격 동기로 스케줄이 생기는 경우는 막을 수 없다. 이 경우에는 스케줄 변화 직후 잠깐 빠른 시작을 다시 disabled 로 두거나, 카드를 버튼 아래로 삽입하는 식의 완충을 검토한다.

## M-2 · 「새 루틴 만들기」는 판단 전에도 누를 수 있고 위치가 바뀐다 — 새 e2e 는 이를 재지 않는다

- 근거
  - `RoutinesClient.tsx:452-461` — `btn-new-routine` 에는 `disabled` 가 없다.
  - 판단 전에 버튼 줄 위에 있는 것은 `NextCardSkeleton` 한 장뿐이다(`:422`, 스켈레톤 `:1024-1037`). 판단 뒤에는 「오늘 카드 + 놓친 루틴」 두 장이 되거나(down), 주 행동이 quick(휴식일·오늘 이미 운동)이면 0장이 된다(up).
  - `routinesLoaded` 전에는 스켈레톤조차 없다. 따라서 스켈레톤이 생기는 순간에도 한 번 내려간다.
  - e2e `home-primary.spec.ts:96-101` 의 `__quickTops` 는 빠른 시작이 enabled 일 때만 기록한다. 새 테스트(`:369-371`)는 새 루틴 버튼의 위치 변화를 기록하지 않는다. 판단 뒤 최종 y 순서만 본다.
- 실패 시나리오
  - 아래로 밀리는 경우, 원래 자리에는 놓친 루틴 카드의 왼쪽(이름·「n일 전」) 영역이 온다. 비대화형이라 헛탭으로 끝난다. 사용자는 새 루틴 버튼이 안 눌렸다고 느낀다.
  - 위로 밀리는 경우(스켈레톤 소거), 원래 자리에 버튼 줄 아래의 오늘 안내 카드나 「내 루틴」 행 왼쪽이 온다. 현재 행·카드의 시작 버튼은 모두 오른쪽 끝이라 운동이 잘못 시작되지는 않는다.
  - 결과가 「운동 시작」은 아니어서 H 는 아니다. 그래도 왼쪽 레이아웃이 바뀌면(예: 행 전체 탭) 바로 오탭이 된다.
- 권고(택1)
  - (a) 새 루틴도 판단 전에는 disabled 로 둔다. 같은 줄 두 버튼의 일관성도 맞는다.
  - (b) 버튼 줄을 카드보다 위로 고정한다.
  - (c) 스켈레톤 높이를 최종 카드 수에 맞춘다. 스케줄과 놓친 루틴 후보가 있으면 두 장으로 잡는다.
  - 어느 쪽이든 e2e 관찰기에 `btn-new-routine` 의 enabled 동안 top 기록을 추가한다.

## L-1 · `getCompletedDayNumsSince` 가 끝나지 않으면 홈이 영원히 판단 전 상태

- 근거: `RoutinesClient.tsx:169-173`, `:292`. 스케줄 사용자에게 새 대기 조건이 하나 생겼다. 예외는 `.catch→.finally` 로 덮인다. 그러나 promise 가 resolve 도 reject 도 되지 않는 경우(Loki 어댑터 미준비 등)에는 빠른 시작이 영구 disabled 로 남는다. 추천 쪽에도 같은 성질이 이미 있다. 그래서 새 위험 등급은 낮다.
- 그 밖의 경로는 문제없다.
  - recoKey 변경: 이전 effect 가 `cancelled` 되고 새 effect 의 `.finally` 가 `setDoneLoaded(true)` 한다.
  - 언마운트: 안전하다.
  - 스케줄이 나중에 생기는 경우: effect 는 스케줄과 무관하게 돌아 이미 true 다.
- 권고: 필요하면 타임아웃(예: 3초) 뒤 `doneLoaded=true` 로 놓는 안전판을 둔다(빈 집합으로 판단).

## L-2 · `doneLoaded` 가 열쇠(recoKey)별로 초기화되지 않음 — 지난 완료일로 판단

- 근거: `doneLoaded` 는 한 번 true 가 되면 계속 true 다(`:103`, `:173`). 자정이 지나 `todayNum` 이 바뀌면 추천은 열쇠 불일치로 null 이 되고 다시 기다린다. 완료일은 지난 집합을 그대로 쓴다.
- 시나리오: 자정 넘어 포커스로 돌아오면 새 추천이 완료일보다 먼저 도착할 수 있다. 이때 지난 8일 창으로 `missedCatchUp` 을 계산한다. 같은 데이터라 대개 결과가 같다. 그러나 창 경계 날이 달라지면 판단 뒤에 놓친 루틴 카드가 나타나거나 사라질 수 있다. 버튼은 그 순간 enabled 다.
- 권고: 완료일도 `{key, value}` 로 보관하고 열쇠가 다를 때는 미로딩으로 본다. 추천과 같은 방식이다.

## L-3 · 판단 뒤 놓친 루틴 카드가 사라지는 기타 경로

- 동기로 그 루틴이 지워지면 `name=null` 이 되어 카드가 `null` 을 반환한다(`:1379`). 버튼 줄이 위로 올라간다.
- `Date.now()` 를 렌더마다 읽으므로(`:273-276`) 포커스 이벤트 없이 자정을 넘긴 리렌더에서도 `catchUp` 이 바뀔 수 있다.
- 드문 경로라 L 이다. M-1 의 완충 방안을 적용하면 함께 완화된다.

## L-4 · 새 e2e 가 「판단 전에 놓친 루틴이 떴다 사라지지 않는다」를 직접 재지 않는다

- 근거: `home-primary.spec.ts:335-371`. 최종 y 순서와 `quickTops≤1` 만 본다. 그런데 이번 변경의 (b) `homeReady && catchUp` 는 빠른 시작이 disabled 인 동안의 일이다. `quickTops` 로는 회귀가 잡히지 않는다. `homeReady &&` 를 빼도 이 테스트는 통과할 가능성이 높다.
- 권고: 관찰기 rAF 에서 `home-ready` 가 붙기 전에 `catchup-card` 가 존재했는지 플래그로 기록하고 false 를 단언한다. M-2 와 같은 맥락에서 새 루틴 top 기록도 넣는다.
- 참고: 「어제」 배정 + 오늘 배정 시나리오는 오늘이 어떤 요일이어도 성립한다(`(d+6)%7`). 문제없다.

## L-5 · 원본 보존 규칙(CLAUDE.md §3.6) 부분 이탈

- `RoutinesClient.tsx:480` — 옮기기 전 놓친 루틴 JSX 블록이 **삭제**되었다. 남은 것은 한 줄짜리 `[원본]` 설명뿐이다. 규칙은 「기존 호출부는 주석 처리」이므로 원래 블록을 `{/* [원본] ... */}` 로 남겨야 원복이 쉽다. 순서만 바꾼 이동이라 실질 위험은 낮다.
- `:286-292` — `homeReady` 식에 조건을 덧붙이면서 직전 버전(v0.54.0, `doneLoaded` 없는 식)을 `[원본]` 으로 남기지 않았다. 기존 `[원본]` 주석은 그보다 더 이전 식을 가리킨다.
- `:424-426` — 새 블록 위의 `[개선] … @plm SRS-093` 주석과, 따라 옮겨 온 기존 두 줄 주석이 겹친다. 정리할 수 있다(무해).

## 확인했고 문제없는 것

- 버전: 웹은 `src/frontend/package.json` 하나만 올리는 관례다(직전 v0.52~0.54 커밋 동일). 픽스이므로 patch 0.54.1 이 맞다.
- 빨강 채움: 놓친 루틴 카드는 `variant="secondary"`(`:1398`)라 brand 관찰(`seen`/`atReady`)에 영향이 없다. 스케줄이 없는 사용자의 `homeReady` 시점은 변하지 않는다.
