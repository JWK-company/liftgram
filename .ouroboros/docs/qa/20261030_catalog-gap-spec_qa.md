## M — 이번 작업에서 고치거나 스펙에 결정을 남긴다

### M-1. 「대체 후보는 family·similar·패턴으로 나온다」는 스펙 서술이 사실과 다르다 — 새 113종목의 상세 「대체 운동」은 비어 있다
- `movementPatterns.ts:344,349` `movementPatternOf/samePatternIds`를 런타임에서 부르는 곳이 없다(`grep -rn samePatternIds src` 결과는 정의와 테스트뿐). 그래서 패턴 67개 추가는 화면에 아무 영향이 없다.
- 서버 상세(`frontend/app/exercise/[id]/page.tsx:77`)는 서버의 `substitute_ids`만 쓴다. 그런데 생성 SQL(`scripts/gen-catalog.mjs:202-206` VALUES)에는 substitute_ids가 없어서 새 행은 기본값 `'{}'`다. 기기 `SUBSTITUTES`(`core/src/data/seed/substitutes.seed.ts`)에도 새 키가 없다. 기기는 같은 주동근으로 폴백한다(`exerciseRepository.ts:178-183`).
- 수정: (a) 스펙 §3의 패턴 행 설명을 「현재 소비처 없음(장래 대비)」으로 고친다. (b) 대체 운동을 원하면 새 종목 키를 `SUBSTITUTES`에 추가하고(같은 family·similar 상위 3~5) 서버 `substitute_ids`를 채우는 SQL을 만든다. 0016 방식으로 하거나 생성기 열에 추가한다. 아니면 「새 종목 상세의 대체 운동 = 비어 있음(허용)」을 §6 「하지 않는 것」에 적는다.

### M-2. 「운영 커스텀 종목 0개 → 이름 충돌 없음」은 잘못된 테이블을 본 근거다
- 기기에서 만든 커스텀 종목은 서버 `exercises` 테이블로 가지 않는다. `sync_records(collection='exercises')`로 간다(`database/migrations/0011_sync.sql:11`, `core/src/sync/catalogFilter.ts:24` — is_custom 행만 동기). 앱의 「종목 만들기」는 로컬 `createCustomExercise`(`exerciseRepository.ts:115`)라서 서버 `exercises.is_custom`은 구조상 거의 0이다.
- 서버 `name_ko` UNIQUE(`0000_init.sql:44`)는 이 경로와 상관없다. 문제는 사용자 화면이다. 같은 이름(또는 가져오기로 만든 `cx-*` 커스텀, 예: Hevy의 「Single Leg Romanian Deadlift」)이 있으면 목록에 두 줄이 생기고 기록이 갈린다. `getExerciseIdsByNameKo`(`exerciseRepository.ts:11-17`)는 nameKo가 같으면 마지막 행이 이긴다.
- 수정: 배포 전에 `SELECT payload->>'name_ko', count(*) FROM sync_records WHERE collection='exercises' AND NOT deleted AND (payload->>'is_custom')::boolean GROUP BY 1`를 돌려, 새 113종목의 이름·별칭(normalizeNameKey 기준)과 대조한 결과를 스펙 §4에 적는다. 겹치는 것이 있으면 사용자별로 안내하거나 합치는 계획을 세운다.

### M-3. 기존 family에 새로 생긴 39개 「기구 칸」이 옛 기록을 매 부팅 옮길 수 있다 — dry-run 필요
- 새 행 39개가 기존 family의 빈 기구 자리를 채운다(예: `plank/kettlebell → 플랭크 풀 스루`, `lateral_raise/barbell → 랜드마인 레터럴 레이즈`, `sit_up/machine → GHD 싯업`, `incline_fly/machine`, `neck_extension/machine`, `sumo_deadlift/dumbbell` 등).
- 지금까지 `no-sibling`으로 남아 있던 옛 블록(variant_equipment 칸이 남은 기록)은 `catalogMigrationPlan.ts:138`(규칙 2)에 따라 새 종목으로 **옮겨진다**. 비머신 종목에 브랜드 키가 남은 블록은 `:155`(규칙 3)에 따라 새 머신 형제로 옮겨진다(예: 싯업 + 브랜드 → GHD 싯업). 정규화는 버전 표식 없이 부팅·동기마다 돈다(`catalogNormalize.ts:4-7`).
- 수정: 운영 `sync_records`(workout_exercises·routine 블록)에서 「exercise_id ∈ 해당 family의 기존 종목, variant_equipment ∈ 새로 채워진 기구 또는 브랜드 키」 건수를 센다. 아니면 서버 이관 dry-run(`be/cmd/migrate-records`와 같은 계획)을 새 표로 돌려 바뀌는 블록 목록을 스펙 §4에 적는다. 0건이면 닫는다. 건수가 있고 의미가 틀린 이동이면(플랭크 → 풀 스루 등) `migration-overrides.csv`로 막거나 M-4처럼 family를 분리한다.
