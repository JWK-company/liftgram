## 총평

핵심 흐름은 스펙대로 동작한다. 연결 id 우선 짝짓기, 완료 직전 스냅샷, 한 번의 write, 처방 루틴 잠금(D5), 운동 중 질문 제거(D3), 무게·변형 미저장(D4), 기본 이름과 「(2)」 규칙이 모두 맞다. 사용자 예시(벤치 교체 + 플라이 2→3에서 플라이만 반영)를 손으로 따라가 봐도 결과가 정확하다.

결함은 **슈퍼셋 처리**에 모여 있다. 슈퍼셋은 D1이 변경으로 치는 항목인데 두 곳이 어긋난다.
- 추가 종목과 묶은 슈퍼셋을 변경으로 감지하지 못한다.
- 「슈퍼셋」 한 항목을 체크하면, 바뀌지 않은 다른 묶음까지 풀린다.

이 밖에 sortOrder 동점 때문에 추가 종목이 엉뚱한 자리에 들어가는 문제가 있고, 스펙이 약속한 저장소 테스트가 빠졌다. 치명 결함은 없다.

## 높음

### H1. 추가 종목과 묶은 슈퍼셋이 변경으로 감지되지 않고, 반영하면 묶음이 사라진다
- 파일:줄: `src/core/src/domain/routineDiff.ts:156-170` (`both` 필터), `:280-303`
- 재현(프로브로 확인)
  - 입력: 루틴 a, b(묶음 없음). 오늘 a 다음에 c를 즉석 추가하고 a와 c를 슈퍼셋(S)으로 묶었다.
  - 결과: 변경 목록이 `["add:wc"]`뿐이고 `superset` 항목이 없다. 기본 선택으로 반영하면 c는 `group: null`로 생긴다. 사용자가 만든 a+c 슈퍼셋은 루틴에 남지 않고, 선택할 길도 없다.
- 원인: 묶음 비교를 「양쪽에 다 있는 줄(`both`)」끼리만 한다. a의 오늘 그룹 S가 `both` 안에서는 혼자라서 `partitionKey`가 1인 그룹으로 보고 버린다.
- 수정안: 묶음 비교 대상에 「완료 세트가 있는 추가 블록」을 포함한다. 키는 블록 id로 쓴다. 이렇게 하면 S={a, c}가 잡힌다. 반영할 때는 `add`와 `superset`이 함께 선택된 경우에만 새 줄에 그룹을 준다. 지금 코드도 그렇게 하고 있으므로 감지만 고치면 된다. 테스트: 「추가 종목 + 기존 줄 슈퍼셋 → superset 항목 생김 → 둘 다 선택하면 같은 그룹」.

### H2. 「슈퍼셋」 항목을 체크하면 오늘 건너뛴 줄이 속한, 바뀌지 않은 묶음까지 풀린다
- 파일:줄: `src/core/src/domain/routineDiff.ts:248`, `:280-282`, `:293`
- 재현(프로브로 확인)
  - 입력: 루틴 a+b 슈퍼셋(G), c, d. 오늘은 b를 건너뛰었다(세트 0). c와 d를 새로 슈퍼셋(H)으로 묶었다.
  - 변경 목록: `remove:r2`(기본 해제), `superset`.
  - 사용자는 c+d 슈퍼셋만 남기려고 `superset`만 체크했다.
  - 결과: `r1(a).group = null`이 된다. b는 그룹 G에 홀로 남는다. 바꾸지 않은 a+b 슈퍼셋이 루틴에서 깨진다.
- 원인: `tokens`를 만들 때 `live()`가 거른 블록(세트 0)만 제외된다. 그래서 a는 1인 그룹으로 보고 null이 된다. b 줄은 `it.block`이 없어 갱신되지 않고 옛 G를 유지한다. 「선택한 것만 반영」이라는 원칙을 묶음 단위에서 어긴다.
- 수정안: 다음 중 하나를 쓴다.
  - (a) 반영할 때 그룹 멤버를 셀 때, 남겨 둔 비-live 줄도 그 줄의 **루틴 그룹**으로 포함한다. 바뀌지 않은 묶음은 기존 그룹 id를 그대로 유지한다.
  - (b) 더 단순하게: 오늘 묶음 구성이 루틴과 같은 그룹(멤버 집합이 같거나, 건너뛴 멤버만 빠진 경우)에는 `u.group`을 설정하지 않는다(undefined = 그대로).
  - 테스트: 위 시나리오에서 a와 b의 그룹이 그대로인지 확인한다.

## 중간

### M1. sortOrder 동점이면 추가 종목이 오늘 위치보다 앞에 들어간다
- 파일:줄: `src/core/src/domain/routineDiff.ts:268-275`. 근본 원인은 `src/core/src/data/workoutRepository.ts:675-700`(`addExerciseToWorkout`의 `sortOrder = count`)과 `:732`(`removeWorkoutExercise`가 sortOrder를 다시 매기지 않음)이다.
- 재현(프로브로 확인)
  - 입력: 루틴 a, b, c(블록 0, 1, 2). 운동 중 b 블록을 지우고 x를 추가했다. count가 2이므로 x의 sortOrder는 2가 되어 c와 같다. 화면에서는 x가 c 뒤에 보인다(의심: 동점일 때의 표시 순서).
  - 결과: 반영 계획이 `r1:0, x:1, r3:2`가 된다. x가 c 앞에 들어간다. 앵커 루프가 `x.sortOrder >= b.sortOrder`에서 c를 만나 멈추기 때문이다.
  - 같은 동점에서 `order`를 선택한 분기는 c, x 순서가 된다. 두 분기의 결과가 서로 다르다.
- 수정안: 다음 중 하나를 쓴다.
  - (a) `addExerciseToWorkout`이 `max(sort_order)+1`을 쓰게 바꾼다. 원본 줄은 보존 규칙에 따라 주석 처리한다.
  - (b) `getSessionBlocks`가 sortOrder를 화면과 같은 기준(sort_order, 그다음 created_at)으로 정렬한 **순번(0..n)**으로 다시 매겨서 넘긴다. 순수 함수 쪽을 고치지 않아도 되는 (b)를 권장한다.

### M2. 교체된 줄의 「세트 수」 항목이 새 종목 이름으로 표시되지만, 실제로는 원래 종목 줄에 적용된다

## 확인했고 문제없음

- **예시를 손으로 따라가 봄**
  - 루틴: r1 바벨 벤치 3, r2 플라이 2. 블록: w1 덤벨 벤치(연결 r1, 워킹 3), w2 플라이(연결 r2, 워킹 3).
  - diff 결과는 `swap:r1`과 `sets:r2(2→3)`이다. r1은 3=3이라 세트 변경이 없다.
  - `sets:r2`만 선택하면 r1은 `{sortOrder:0}`만 바뀌고(종목 그대로) r2는 `targetSets:3`이 된다. 정확하다. e2e 1번도 루틴을 다시 시작해 확인한다.
- **선택하지 않은 항목이 정말 그대로인지**: swap, sets, remove, add, order 모두 그대로다(add를 끼우면 상대 순서는 유지된 채 번호만 다시 매겨진다). superset만 H2 예외가 있다.
- **같은 종목이 두 줄일 때**: 연결 id로 정확히 구분한다. 같은 연결 id를 가진 블록이 둘이면 두 번째는 추가로 본다.
- **운동 중 지우고 같은 종목을 다시 추가한 경우**: 폴백이 원래 줄과 짝지어 변경 없음(또는 order만)으로 처리한다. 합리적이다.
- **슈퍼셋 그룹 id 충돌**: 반영과 저장 모두 `groupIdMapper`가 새 `ss_` id를 발급한다. 세션 그룹 id나 다른 루틴(`duplicateRoutine`이 복사한 id)과 겹치지 않는다.
- **원자성**: `applyRoutineChanges`와 `saveWorkoutAsRoutine`은 각각 `database.write` 한 번 안에서 `batch` 한 번으로 실행된다. 대상 테이블(`routines`, `routine_exercises`)은 `USER_TABLES`에 들어 있어 동기된다. `blockRecords`는 write 밖에서 읽지만, 대상이 완료 세트가 있는 블록(완료가 지우지 않음)뿐이라 안전하다.
- **v24**: `addColumns`(optional)를 쓰고, `schema.ts`와 모델이 동기돼 있다. 첫 동기에서 커서를 재설정하는 경로(QA H2)가 그대로 적용된다. 서버 `UpsertSyncRecords`가 얕게 병합(`payload || EXCLUDED`)하므로, v23 기기가 올려도 `routine_exercise_id`가 지워지지 않는다.
- **이관·백업**: 이관 스크립트(`scripts/migrate-records.ts`)는 부분 패치만 하므로 새 키에 영향이 없다. 백업(`sync/backup.ts`)은 raw를 그대로 복사하고 id를 보존하므로 연결이 유지된다. 오래된 백업은 연결이 없어 폴백으로 처리된다.
- **루틴으로 시작하는 경로**: `startWorkoutFromRoutine`(`workoutRepository.ts:580`) 하나뿐이고, 여기서 연결을 채운다. 교체(`swapWorkoutExercise`)는 같은 행을 update하므로 연결이 유지된다.
- **완료 확인을 두 번 누르는 경우**: 확인을 누르면 대화상자를 즉시 닫고, 완료 버튼은 `busy` 동안 비활성이다. 반영·저장 버튼도 `loading` 동안 비활성이다(`Button.tsx:58`). 새 위험은 없다.
- **시트 상태 전이**: 각 단계에서 닫으면 다음으로 간다.
  - 선택 단계 닫기 → 오늘만
  - 항목 체크 닫기·취소 → 선택 단계
  - 이름 단계 취소 → 루틴 운동이면 선택 단계, 빠른 운동이면 「저장 안 함」 후 종료
  - 이름 입력은 공백만 있으면 저장이 비활성이고, 저장 때 trim과 중복 「(2)」를 적용한다.
- **D3 제거의 영향**: 호출하던 2곳만 주석 처리했다. `askRoutineScope`와 `swapScope` 시트는 원복용으로 남겨 두었다(죽은 코드이지만 보존 규칙에 맞다). 다른 호출자는 없다. `make verify`(lint 포함)를 통과한다.
- **D4**: `targetWeightKg`, `machineVariant`, 변형 칸이 모두 null이다. 교체를 반영하면 변형 칸 7개를 비운다.
- **D5**: 루틴 줄 중 하나라도 처방이 있으면 `canApply=false`가 되어 「바꾸기」가 비활성되고 안내 문구가 뜬다. 「새 루틴으로 저장」은 쓸 수 있다.
- **i18n**: 웹은 `lang`이 "ko"로 고정이라, `suggestNameForWorkout`이 lang 인자를 받지 않아도 지금은 영향이 없다.
