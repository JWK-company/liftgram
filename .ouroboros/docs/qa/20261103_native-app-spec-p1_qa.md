## 판정: **조건부**

§12.2 는 1차 H-1(값 덮어쓰기)과 H-5(순서 규칙 부재)를 실제로 막았다. H-3(ack)도 방향은 맞다. 그러나 아래 네 곳에서 결함이 그대로 남거나 새로 생겼다(H 5건).
- H-2(세대·순서)의 rebase 가 **무엇을 기준으로 다시 적용하는지**(자리인지 세트 id 인지)와 `appliedThroughSeq` 를 **언제 어디서 잡는지**가 정해지지 않았다. 웹 화면의 변경(seq 없음)이 끼면 1차의 「카드가 되돌아가 세트가 유실」 시나리오가 다시 재현된다.
- 「멱등은 DB 상태로만」 규칙 때문에, ack 되지 않은 조작이 **사용자가 앱에서 해제한 세트를 다시 완료**한다. ack 가 막히는 경로는 실제로 있다.
- 「휴식 정본 = 네이티브 현재 `endsAt`」은 웹 화면에서 시작하거나 끝낸 휴식과 **두 주인**이 된다. 마지막에 도착한 값이 이기므로 끝낸 휴식이 되살아나고 +30초가 사라진다.
- H-4 의 미리 계산은 「탑셋 뒤」만 다룬다. 「1RM 의 N%」는 완료할 때마다 다시 채워지는 연쇄라서, 카드에 보인 무게와 실제로 저장되는 무게가 달라진다. H-1 개정으로 조작에 값을 싣지 않으므로 이 어긋남을 잡을 장치도 없다.

아래 H 5건을 고친 뒤 이 절만 3차 확인(짧게)을 거치면 P1 을 시작해도 된다.

## H — 구현 전 반드시 고칠 것

### H-1. rebase 기준이 정해지지 않았다: 「자리(queue[0] 빼기)」로 다시 적용하면, 웹 화면 완료와 겹칠 때 1차 H-2 유실이 그대로 재현된다
- **근거**
  - §12.2 H-2: 「스냅샷을 받으면 `seq > appliedThroughSeq` 인 남은 조작을 그 위에 다시 적용(rebase)」이라고만 적혀 있다. §4.4 의 네이티브 동작은 「`queue[0]`(묶음이면 묶음 전체)의 setIds … 사본에서 그 단계를 빼고」, 즉 **자리 기반**이다.
  - 웹 화면의 완료·해제·값 수정은 seq 가 없다(`ExerciseBlock.tsx:464` `repo.setSetDone(s.id, next)` · `ActiveWorkout.tsx:747` `completeSupersetRound`). 그래서 스냅샷은 「seq 와 무관하게 앞당겨진 상태」를 실어 올 수 있다.
  - 안드로이드는 앱이 앞에 있어도 알림 창을 내려 「세트 완료」를 누를 수 있다. §4.4 의 「앱이 앞에 있을 때 … action 이벤트(즉시)」가 바로 이 경로다.
- **실패 시나리오**(안드로이드 · 앱이 앞에 있음)
  1. 카드는 3세트다. 사용자가 화면에서 3세트를 체크하는 것과 거의 같은 때 알림 창의 「세트 완료」를 누른다. 조작 c7 = `{seq:7, setIds:[set3]}`이고, 네이티브 사본은 4세트로 넘어간다.
  2. 웹은 화면 완료 뒤 스냅샷을 보낸다(`appliedThroughSeq=6` · `queue[0]=set4`).
  3. 네이티브가 c7 을 **자리 기반**으로 rebase 하면 `queue[0]`(=set4)을 빼서 카드에 5세트를 보인다. drain 은 c7 을 적용하지만 set3 은 이미 완료라 아무 일도 없다. **set4 는 완료되지 않았는데 카드는 5세트**다. 사용자는 4세트를 했다고 믿는다(1차 H-2 와 같은 유실).
  - 반대 경우도 있다. 사용자가 화면에서 set3 을 **해제**했고 c7 이 set2 를 겨냥했다면, 자리 기반 rebase 는 set3 을 빼 버려 카드에서 해제한 세트가 사라진다.
- **고칠 방법**
  - rebase 를 **id 기반**으로 정의한다. 스냅샷 `queue` 에서 `action.setIds` 와 겹치는 단계를 뺀다. 겹치는 단계가 없으면 아무것도 하지 않는다(이미 화면에서 처리됨).
  - 네이티브의 버튼 처리도 같은 함수로 한다(누른 순간 보이던 단계의 setIds 를 조작에 고정하고, 사본에서는 그 id 를 가진 단계를 뺀다). 자리 연산은 금지라고 스펙에 한 줄 적는다.
  - core 순수 함수 `rebaseLockQueue(snapshot, pending) → queue` 로 만들고 네이티브(Kotlin/Swift)는 같은 표로 테스트한다. 위 1~3번과 해제 사례를 표에 넣는다.

### H-2. `appliedThroughSeq` 를 언제·어디서 잡는지 정하지 않았다: 스냅샷 읽기보다 늦게 잡거나 새로고침·새 세션을 지나면 거짓 진척이 되어 rebase 가 빠진다
- **근거**
  - §12.2 H-2 는 `appliedThroughSeq` 를 스냅샷에 싣는다고만 한다. M-6 개정으로 스냅샷은 셸(`SessionProvider`)이 저장소에서 **비동기로** 만들고(`SessionProvider.tsx:59-67`처럼 동적 import 뒤 읽기), drain 은 별도의 한 줄 적용기다. 둘 사이의 순서 약속이 없다.
  - §4.2 는 「세트 완료/해제」 때마다 스냅샷을 보낸다. 그래서 drain 이 c5·c6·c7 을 적용하는 **도중에도** 스냅샷이 나간다.
  - seq 의 범위(세션마다 다시 시작하는지, 앱 전체에서 단조 증가하는지)가 적혀 있지 않다.
- **실패 시나리오**
  - 스냅샷 생성이 DB 를 읽기 시작한다(c5 까지 반영된 상태). 그사이 drain 이 c6 을 적용하고 적용 번호를 6 으로 올린다. 스냅샷이 끝날 때 `appliedThroughSeq=6` 을 붙인다. 네이티브는 c6 을 rebase 하지 않으므로 카드가 c6 의 세트로 **되돌아간다**. 사용자가 그 세트(이미 완료)에 「세트 완료」를 누르면 아무것도 기록되지 않는다. 실제로 한 세트가 유실된다.
  - 웹뷰가 새로고침(서비스 워커 갱신·OS 회수)되면, 적용 번호를 메모리에 두었을 경우 0 으로 돌아가고 localStorage 에 두었을 경우 남는다. 남는 쪽이면 flush 전에 kill 됐을 때 DB 에는 없는 적용을 「적용됨」으로 주장한다.
  - seq 를 세션마다 1 부터 다시 매기면, 같은 문서에서 이어서 시작한 새 운동의 c1·c2 가 앞 운동의 `appliedThroughSeq` 보다 작아 rebase 되지 않는다.
- **고칠 방법**
  - 스냅샷 생성을 **drain 과 같은 한 줄(mutex) 안에서** 한다. 또는 읽기 **전에** `appliedThroughSeq` 를 잡는다(그 값 이하의 적용은 읽기에 반드시 들어 있다).
  - `appliedThroughSeq` 의 정본은 아래 H-3 의 **DB 안 워터마크**로 한다. 메모리나 localStorage 에 따로 두지 않는다.
  - seq 는 설치 단위로 단조 증가하고 절대 다시 쓰지 않는다(네이티브 저장소에 카운터). 또는 비교를 `(sessionId, seq)` 쌍으로 한다. 둘 중 하나를 적는다.

### H-3. 「멱등은 DB 상태로만」 때문에, ack 되지 않은 조작이 사용자가 앱에서 해제한 세트를 다시 완료한다. 그리고 ack 가 막히는 경로는 실제로 있다
- **근거**
  - §12.2 H-3: 「멱등은 DB 상태로만(이미 완료면 no-op) — prefs 적용 로그 없음」 · 「아니면 ack 하지 않고 다음 drain 에서 재시도」.
  - 완료된 세트는 화면에서 숫자를 고칠 수 없다(`SetRowEdit.tsx:337,360` `disabled={isDone}`). 잠금 중 완료한 세트를 바로잡으려면 사용자는 **체크를 해제**해야 한다. 웹 동작에서 해제는 흔하다.
  - ack 가 막히는 실제 경로는 세 가지다.
    - ① 쓰기 주인은 시작 뒤 **나중에** 정해진다(`tabGuard.ts:213-226`). 순서는 import 판정 ping(`PING_MS=250` · `:34`) → 스키마 가드 → `claimWriter()`이고, 그 전까지 `getWriterState()`는 `"unknown"`이다(`:341,455`). §4.4 「화면 첫 로드」 drain 은 이 시간대에 돈다.
    - ② `flushLocalDbResult()`는 `"failed"`·`"unreachable"`도 돌려준다(`localDb.ts:48,68-85`). `"unreachable"`은 어댑터 내부 구조가 바뀌면 **영원히** 계속된다(prefs 는 이 경우를 받아들인다 · `prefs.ts:160-162`).
    - ③ ack 하지 못했을 때 재시도를 깨우는 계기가 없다. 다음 drain 은 resume·첫 로드·새 조작 때뿐이다.
  - M-12 (h)「잠금 중 완료 세트를 앱에서 해제 후 drain」은 테스트 이름만 있고 기대 결과 규칙이 없다.
- **실패 시나리오**
  - 잠금 중 set2 를 완료한다(c4). 앱을 열면 첫 로드 drain 이 c4 를 적용하지만 writer 가 `"unknown"`이라 ack 하지 않는다. 사용자가 무게가 틀린 것을 보고 set2 를 **해제**한다. 그다음 다른 앱을 잠깐 보고 돌아오면 resume drain 이 c4 를 다시 적용한다. set2 가 다시 완료되고 `completedAt` 은 잠금 때 시각이 된다. 사용자의 해제가 조용히 되돌려진다.
  - `"unreachable"`이 계속되면 대기열이 끝없이 쌓인다. rebase 할 조작도 계속 늘어난다(상한 없음).
- **고칠 방법**
  - 적용 워터마크(`lockAppliedSeq`, 세션 id 포함)를 **같은 Loki DB 안**에 쓴다. 기록과 같은 내려쓰기에 실리는 로컬 전용 저장소(예: Watermelon `database.localStorage`나 동기하지 않는 로컬 표)를 쓴다. drain 은 `seq ≤ 워터마크`이면 건너뛴다. 이렇게 하면 kill 에도 안전하고(워터마크와 기록이 함께 남거나 함께 사라진다), 해제도 보존된다. 1차가 없앤 「적용 로그」를 **디스크 원자성이 있는 자리**로 되살리는 것이다.
  - ack 조건은 「워터마크를 포함한 내려쓰기가 `"saved"`」로 한다. `getWriterState()==="owner"` 조건은 빼거나 「`"lost"`·`"framed"`가 아님」으로 바꾼다. `"sealed"`는 flush 결과가 이미 걸러 주고, `"unknown"`이 첫 로드를 막기 때문이다. 아니면 drain 을 writer 판정(claim)이 끝날 때까지 미룬다.
  - ack 에 실패하면 짧은 백오프 타이머(예: 2·5·15초)로 drain 을 다시 깨운다. `"unreachable"`일 때의 정책(prefs 처럼 받아들일지, 「앱 열기」로 막을지)을 한 줄 정한다.
  - M-12 (h) 기대값: 「해제가 남는다(다시 완료되지 않는다)」.

### H-4. 휴식에 주인이 둘이다: 「네이티브 현재 `endsAt`이 정본」과 「웹이 스냅샷으로 휴식을 보낸다」가 함께 있어 마지막에 도착한 값이 이긴다
- **근거**
  - §12.2 H-2: 「휴식 정본은 잠금 중 네이티브의 현재 `rest.endsAt` 하나 — drain 끝에 네이티브 현재값을 받아들인다 · `queue.drain()`이 `{actions, rest}`를 준다」.
  - 그런데 웹도 휴식을 시작하고 끝낸다. 화면 완료는 `onStartRest(restSecondsForSetType(...))`(`ExerciseBlock.tsx:468-470`)를 부르고, 「휴식 끝내기」는 `clearRest`(`SessionProvider.tsx:85-89`)다. §4.2 의 스냅샷 `rest` 가 이것을 네이티브로 보낸다. 네이티브가 스냅샷의 `rest` 를 받아들이는지, 자기 값을 지키는지 규칙이 없다.
  - 웹은 「잠금 중」인지 알 수 없다. drain 은 앞에 있을 때의 action 이벤트로도 돈다(§4.4).
  - `drain()`이 돌려준 `rest` 는 **drain 을 시작한 시각의 값**이다. 적용(비동기 · 수백 ms)이 끝날 때 받아들이면 그 사이의 변경을 놓친다.
- **실패 시나리오**
  - (끝낸 휴식이 되살아남) 화면에서 「휴식 끝내기」를 누른다(웹 `null`). 스냅샷은 저장소를 비동기로 읽어 만드는 중이다. 그때 알림 창의 조작 이벤트로 drain 이 돌고, 네이티브의 옛 `endsAt`을 돌려받아 `startRestUntil`로 다시 건다. 끝낸 휴식이 웹과 잠금화면 양쪽에서 되살아나고, 휴식 끝 알림이 울린다.
  - (+30초가 사라짐) 앱이 앞에 있을 때 알림 창에서 +30초를 누른다(네이티브 E+30). 바로 앞에 만들어진 웹 스냅샷(rest=E)이 뒤늦게 도착한다. 네이티브가 그것을 받아들이면 E 로 되돌아가고 알람도 앞당겨 다시 예약된다.
  - (웹 휴식을 지움) 화면에서 세트를 완료해 웹 휴식 E_w 가 시작됐는데, 스냅샷이 도착하기 전에 resume drain 이 돌면 네이티브의 `null`을 받아들여 E_w 를 지운다.
- **고칠 방법**
  - 휴식을 **값 + 의도 시각**으로 만든다: `rest = {endsAt, totalSec, setAt, by:"web"|"native"}`. 양쪽 모두 「`setAt` 이 더 늦은 쪽이 이긴다(LWW)」로 합친다. 네이티브는 스냅샷의 `rest.setAt`이 자기 값보다 늦을 때만 받아들이고, 웹은 drain 결과의 `rest.setAt`이 자기 값보다 늦을 때만 받아들인다.
  - 웹의 휴식 변경은 스냅샷(비동기 DB 읽기)과 따로 **즉시** `session.setRest(rest)`로 보낸다. 디바운스도 DB 읽기도 거치지 않는다.
  - M-8 의 `liftgram.restEndsAt`에도 `setAt`을 함께 저장한다.
  - 테스트(M-12 d 보강): 웹 끝내기 ↔ 네이티브 drain 경합, 네이티브 +30 ↔ 늦은 스냅샷, 웹 시작 ↔ 스냅샷 전 resume.

### H-5. 처방 무게 미리 계산이 「탑셋 뒤」만 다룬다: 「1RM 의 N%」는 완료할 때마다 다시 채우는 연쇄이고 비동기 입력(`has1rm`)이 필요하다. 카드 값과 저장 값이 어긋나도 잡을 장치가 없다
- **근거**
  - `planPrescribedLoadFills`(`prescription.ts:219-254`): `pct1rm && !has1rm`이면 **워밍업·실패가 아닌 어느 세트를 완료하든**, 그 세트의 추정 1RM 으로 뒤의 손대지 않은 세트를 다시 채운다. 채운 세트는 `userEdited`를 바꾸지 않으므로(`workoutRepository.ts:806-811`은 `weightKg`만 씀) 계속 「손대지 않음」이다(`blockUnit.ts:57-67`). 그래서 2세트를 완료하면 3·4세트가 다시 바뀐다. 「탑셋의 N%」만 `isTop`일 때 한 번 채운다.
  - `has1rm`은 지난 완료 운동을 조회하는 비동기 값이다(`workoutRepository.ts:802` `estimatedOneRmForSlot`). 순수 함수만으로는 미리 계산할 수 없다. 반올림 단위도 블록 단위와 장비에 따라 다르다(`:806` `blockWeightUnit(we)`).
  - §12.2 H-1 로 조작에는 값이 없고 「저장된 값 그대로 완료」한다. 그래서 drain 때 저장된 값과 카드에 보였던 값이 달라도 아무도 모른다.
- **실패 시나리오**
  - 기록이 없는 종목에 「1RM 의 75%」×4 를 처방한다. 잠금 중 1세트(60×8)를 완료하면 스냅샷은 「탑셋 뒤가 아니므로」 미리 계산하지 않거나, 1세트 기준으로 한 번만 계산한다. 그 뒤 2세트를 60×10 으로 완료하면 drain 때 흐름이 3·4세트를 **2세트 기준으로 다시** 채운다. 카드에는 55 가 보였지만 실제로는 57.5 가 저장된다. 사용자가 실제로 든 무게와 기록이 다르고, 볼륨과 PR 도 달라진다.
  - (이 경우 「2세트를 60×10」이라는 숫자 자체도 잠금 중에는 바꿀 수 없다. 프리필 값 그대로 완료된다.)
- **고칠 방법**
  - 미리 계산을 「탑셋 뒤」가 아니라 **대기열 순서 전체에 대한 시뮬레이션**으로 정의한다. 단계 k 를 완료한 결과(채우기 포함)를 단계 k+1 의 입력으로 넘긴다. 입력(`rx`·`has1rm`·장비·블록 단위·세트별 touched 판정 재료 `userEdited`/`updatedAt`/`createdAt`)은 스냅샷 생성기가 저장소에서 모아 순수 함수 `planLockQueueValues`에 넘긴다. drain 의 `completeSetsFlow`와 **같은 함수로** 채우기를 계산한다는 것을 테스트로 고정한다(M-12 c 를 「pct1rm 연쇄」까지 확장).
  - 조작에 **기대 저장값**을 싣는다: `expect: {setId, weightKg(저장 kg), reps}[]`(표시값이 아니므로 1차 H-1 의 왕복 문제가 없다). drain 은 값을 덮지 않고, 다르면 완료는 하되 진단 로그와 함께 그 세트를 「잠금화면에서 본 값과 다름 — 확인」 표식으로 화면에 띄운다. 조용한 어긋남을 사용자에게 보이게 만든다.
  - 그게 어려우면 「`pct1rm` 이고 `!has1rm`인 블록은 첫 완료 뒤 「앱 열기」」로 막는다. 둘 중 하나를 스펙에서 정한다.

## M — 구현 중 반드시 반영

### M-1. 「지금 세트」 순서 규칙(§12.2 H-5)의 모호한 경우: 슈퍼셋 멤버마다 워밍업·건너뛴 세트가 다를 때, 멤버가 이웃하지 않을 때
- **근거**: 규칙 ② 「블록 안 첫 미완료」 + ③ 「`roundKeyOf`가 같은 세트를 한 단계로」 + ④ 「블록의 첫 미완료로 간다」는 **어느 멤버의 첫 미완료가 라운드를 정하는지** 말하지 않는다. 짝 키는 워밍업·드롭·실패에 `null`을 준다(`supersetRound.ts:15-26`). 화면은 블록 `sort_order`가 아니라 **행(row)** 순서로 보인다. 묶음은 첫 멤버 자리에 한 줄로 접힌다(`ActiveWorkout.tsx:221-236`).
- **모호한 경우(규칙 표에 기대값을 정해 넣을 것)**
  1. A=[1,2] · B=[W,1,2](B 에만 워밍업). A 의 첫 미완료 n:1 이 단계 [A1,B1]을 만들면 **B 의 워밍업이 B1 뒤로 밀린다**. 「묶음의 모든 멤버에서 키가 null 인 앞쪽 세트를 먼저 한 단계씩, 그 뒤 라운드」처럼 정해야 한다.
  2. A=[1✓,2] · B=[1,2](길게 눌러 A1 만 완료). A 기준이면 [A2,B2]가 되어 B1 을 건너뛴다. B 기준이면 [B1]이다. 「멤버들 첫 미완료의 **가장 작은 라운드**, 단계에는 미완료 세트만」으로 정한다(`pickRoundSets`는 완료된 짝도 돌려준다 · `:34-46`. 표시·조작에서 빼야 한다).
  3. 묶음 멤버의 `sort_order`가 이웃하지 않을 때(A(g)·C·B(g)): 규칙 ①(블록 `sort_order`)은 A,C,B 이고 화면은 [A+B],C 다. ①을 「화면 행 순서」로 고친다.
  4. 드롭 세트 D 가 일반 세트 사이에 있을 때(A=[1,D,2] · B=[1,2]): [A1,B1] → [A-D] → [A2,B2]가 기대값인지 적는다.
  5. 12단계 상한에서 묶음 한 단계는 1단계로 센다는 것, 묶음 단계의 `setNo/setTotal` 표기(어느 멤버 기준인지)를 적는다.

### M-4. M-7 「값 출처」는 지금 필드로 판정할 수 없다: 스키마 변경(v27)·서버 컬럼·동기·전파 규칙까지 P1 범위다

### M-6. 네이티브 대기열의 읽기-수정-쓰기 원자성이 없다(안드로이드 리시버 ↔ 플러그인 · iOS 의도 ↔ 앱)

## L — 다듬기, 확인

- **L-1.** §4 원안의 낡은 필드와 규칙이 남아 있다. `LockSnapshot.unit`(최상위), `LockStep.weight/reps(표시 단위)`·`groupWithNext`, `rest_set` 조작, 「prefs 최근 200개 적용 id」, 「`queue[1]`(묶음이면 묶음 다음)」이 그렇다. §12 가 이긴다고 해도 구현자가 헷갈린다. §4 에서 지우거나 취소선을 긋고, 개정된 타입 정의를 한 곳에 다시 적는다.
- **L-2.** `lib/e2eFlags.ts`는 빌드 깃발 상수 하나뿐이다. 「기존 결함 주입 틀」은 `ImportFlow readFault` 한 곳이다. 「적용 직후 flush 전 kill」을 주입하려면 drain 안에 새 주입점(예: `E2E_FAULTS && window.__lgFault==="kill-before-flush"`)을 만들어야 한다. 그만큼 작업량을 잡는다.
- **L-3.** 단계의 `setIds`는 스냅샷 때 고정된다. 그 사이 화면에서 묶음을 풀었거나 세트 유형을 워밍업으로 바꿨으면 옛 짝이 함께 완료된다. 「적용 때 짝 키를 다시 계산해 단계가 바뀌었으면 discarded」를 넣을지 정한다.
- **L-4.** `at`은 네이티브 시계다. 기기 시계를 바꿨거나 운동 시작보다 이른 `at`(일시정지 운동)이 들어오면 `completedAt`을 `[startedAt, now]`로 자른다.
- **L-5.** 「discarded: setId 가 이미 완료(완료는 no-op)」는 버림과 성공을 한 목록에 섞는다. 진단에서 구분하도록 `noop`과 `discarded`를 나눈다.
- **L-6.** iOS `pause` 직후 웹뷰가 곧 멈춘다. 「① 입력 커밋 → ② 스냅샷 즉시 전송」이 비동기 DB 읽기를 거치면 끝나지 못할 수 있다. 네이티브 쪽에서 `beginBackgroundTask`로 몇 초를 확보하거나, 커밋 전 입력 값을 스냅샷에 직접 반영하는 길을 적는다(**확인 필요**).

## 요약

§12.2 개정은 1차의 값 덮어쓰기(H-1)와 순서 규칙 부재(H-5)를 막았다. ack 를 디스크 저장에 묶은 방향(H-3)도 맞다. 그러나 동시성과 처방 채우기 쪽에 구멍 다섯 개가 남아 있다.
- **H-1**: rebase 가 자리 기반이면, 웹 화면 완료와 잠금 조작이 겹칠 때 카드가 한 세트 앞서 나가 세트가 유실된다. id 기반으로 정의해야 한다.
- **H-2**: `appliedThroughSeq`를 스냅샷 읽기와 원자적으로 잡지 않거나 새로고침·새 세션을 지나면 거짓 진척이 되어 카드가 되돌아간다.
- **H-3**: 「DB 상태로만 멱등」 때문에, ack 되지 않은 조작이 사용자의 해제를 되돌린다. 첫 로드의 writer `"unknown"`, `"unreachable"`처럼 ack 가 막히는 경로가 실제로 있다. 적용 워터마크를 같은 Loki DB 안에 둬야 한다.
- **H-4**: 휴식에 주인이 둘이라 마지막에 도착한 값이 이긴다. 끝낸 휴식이 되살아나고 +30초가 사라진다. 의도 시각 기준 LWW 와 즉시 전송이 필요하다.
- **H-5**: 「1RM 의 N%」 연쇄 채우기와 비동기 `has1rm` 때문에 「탑셋 뒤」 미리 계산으로는 카드 값과 저장 값이 어긋난다. 조작에 기대 저장값을 실어 어긋남을 드러내야 한다.

M 은 다음과 같다. 순서 규칙의 모호한 경우(워밍업 밀림·건너뛴 라운드·이웃하지 않은 멤버), 슈퍼셋 휴식의 「누른 블록」 부재와 흐름 안 휴식의 충돌, 저장되지 않는 블록 휴식, 값 출처 플래그의 스키마 변경 필요(v27·서버·동기·전파 규칙), 셸 스냅샷의 필드 변경 감지 수단 부재, 네이티브 대기열 원자성, 흐름 추출의 세부 차이, 입력 중 칸이 잠기며 사라지는 값.

판정은 **조건부**다. H 5건을 반영한 뒤 §12.2 만 짧게 3차 확인하고 P1 을 시작하기를 권한다.
