## 설계 판단
1. **counts = 덤프와 같은 스냅샷**: 스펙은 「덤프 직전 REPEATABLE READ」였지만, 그러면 복원 시험(정확히 같아야 ok)이 덤프 몇 초 사이의 쓰기 때문에 거짓 실패를 낼 수 있다. 그래서 세션 하나가 `BEGIN ISOLATION LEVEL REPEATABLE READ; SELECT pg_export_snapshot(); <counts>` 를 열어 두고(fifo · fd 3), `pg_dump --snapshot=<id>` 가 끝나면 COMMIT 한다. 스냅샷을 못 잡으면(10초) 스펙대로 직전 RR 로 세고 detail 에 `counts_approx` 를 붙인다.
2. **복원 시험이 counts 를 찾는 열쇠** = daily 줄 detail 의 `file=<덤프 이름>` 을 `position(:'f' in detail)` 로 찾는다(칸을 하나 더 만들지 않았다). counts 가 없는 덤프(이 기능 전의 덤프)는 `no_counts` 로 실패한다. 그래서 첫 배포 뒤에는 **backup 을 먼저, restore-test 를 그다음** 돌려야 한다.
3. **DB 디스크 여유**는 호스트 `/var/lib/docker`(root 소유라 읽기가 불확실) 대신 컨테이너 안 `df $PGDATA` 로 잰다(pg18 이미지의 PGDATA 경로를 그대로 따른다 · 같은 디스크).
4. psql `-c` 는 `:'var'` 를 치환하지 않는다. 그래서 변수를 쓰는 insert 는 전부 heredoc 표준 입력으로 보낸다.
5. 보고 방아쇠: 엔진은 시도가 끝나는 순간(성공·실패 값)과 `refreshPendingCount` 뒤(미동기 수)에 **두 번** 값을 낸다. 첫 번째에서 보내면 미동기 수가 시도 전 값이라, 「끝남」을 표시해 두고 다음 값이 오거나 2초가 지나면 보낸다. 즉시 조건은 **마지막으로 보낸** 값과 비교한다(1→2 는 쓰로틀, 2→3 은 즉시). 이 기록을 localStorage 에 둬서 새로고침해도 이어진다.
6. 분당 6회 상한은 인스턴스 메모리다(운영은 backend 하나). 여러 대가 되면 그만큼 느슨해질 뿐이고, 상한 자체가 안내용이라 받아들였다.
7. `GetOpsAlert.count` = 경보 이유 수.
8. 문구는 웹에만 쓰지만 moderation 선례를 따라 `core` 사전에 넣었다(WEB_ONLY 는 「제스처를 바꾸며 생긴 이름」만 받는다는 규칙이 있다).

## 남은 걱정
1. **e2e 는 돌려 보지 않았다.** 확인할 것: 동기를 500 으로 막았을 때 `sync-pending` 문구(data-safety 는 abort 를 씀) · 역할을 바꾼 뒤 `reload` 한 번으로 claim·Me 가 admin 이 되는지(Refresh 가 DB 의 사용자를 읽어 발급하는 것은 코드로 확인함) · 백업 줄 판정이 「마지막 줄」이라 **새 DB** 에서 돌려야 한다(머리말에 적음).
2. 첫 배포 순서: 0020 마이그레이션 → `backup-h2500-3.sh` 를 손으로 → 그다음 `restore-test-h2500-3.sh` 를 손으로(반대로 하면 `no_counts` 로 실패 줄이 생긴다). 스펙의 「배포 전 pg_dump(`pre-ops-0020-*.dump`)」는 지금 배포 스크립트에 자동 단계가 없으니 손으로 한다.
3. 복원 시험은 운영 DB 와 **같은 클러스터**에 같은 크기를 한 번 더 쓴다(덤프×3 여유를 확인한다). 덤프가 커지면 복원 시간 동안 IO 가 늘어난다(04:47 · 월 1회).
4. `pg_restore --no-owner` 는 확장(pgvector 등)을 다시 만들므로 컨테이너 계정이 superuser 여야 한다(공식 이미지의 POSTGRES_USER 는 superuser — 로컬에서 됨).
5. 스냅샷 handshake 는 psql 출력이 줄마다 flush 된다는 것에 기댄다(로컬 pg18 컨테이너에서 확인). 안 되면 RR 방식으로 내려가 `counts_approx` 가 붙는다 — 그때 복원 시험이 덤프 몇 초 사이의 쓰기 때문에 거짓 실패를 낼 수 있다(드묾).
